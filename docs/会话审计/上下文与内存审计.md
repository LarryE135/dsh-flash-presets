## 1. 数据与方法

### 1.1 帧结构（Q4 的事实基础）

文件是 7,673 个 zstd 帧首尾相接（每追加一次写一帧），magic `28 B5 2F FD`。

| 指标 | 数值 |
|---|---|
| 帧数 | 7,673 |
| 帧字节：合计 / 均值 / 中位 / p90 / 最大 / 最小 | 11,835,319 / 1,542 / 1,022 / 3,539 / 27,873 / 79 B |
| 每帧事件数：最小 / 中位 / p90 / 最大 | 1 / 2 / 6 / 16（平均 2.77） |
| 帧是否行对齐 | **100%**（7,673 帧全部以 `\n` 结尾，无跨帧残行）→ 任意帧边界都可独立切片 |
| 最大单帧 → 解压 | 27.2 KB → 126.2 KB（2 个事件，位于 turn 2） |
| 最大单事件行 | 93.1 KB（assistant/message，含流式回放块） |

### 1.2 三种「MB」口径必须对齐，否则数字会打架

| 口径 | 数值 | 说明 |
|---|---|---|
| UTF-16 字符数（JS `line.length`） | 44.95 MB | 已有结论里的「44.9 MB」是这个口径 |
| UTF-8 行字节（`Buffer.byteLength`） | 47.32 MB | 本报告分桶统计用这个 |
| 解压后原始字节 | 49.64 MB | 压缩比 4.19× |

差额来自中文（1 字符 = 3 字节 UTF-8 = 1 个 UTF-16 code unit）。**下文凡是「MB」默认指 UTF-8 字节**。

### 1.3 方法

- 读：整文件读入 → `Buffer.indexOf(magic)` 找 7,673 个帧起点 → 逐帧 `zlib.zstdDecompressSync` → 逐行 `JSON.parse`，全程流式聚合，不保留事件对象（峰值 heap 10 MB）。
- 口径校验：`assistant/message.usage.totalTokens = inputTokens + cacheReadTokens + outputTokens`（step 1：16,010+0+167=16,177 ✓），因此 `totalTokens` 就是**该步真实的上下文长度**，这是 Q2 曲线的权威数据源。
- 时长：用 41 组 `turn/start..turn/end` 逐轮累计（15.65 h），不用首末事件差——后者被 `session`/`permission/preset` 等 3 条种子事件的异常时间戳（`createdAt 1792985811385`，比首个 turn 早 **18.96 天**）污染。

## 2. Q1：压实到底多贵

### 2.1 触发机制（配置 + 实测双证）

预设 `flash-lean-ptc-v3` 的 compaction-basic 配置：`thresholdRatio: 0.25`、`retainTokens: 20000`、`compactionRetries: 1`、`auto: true`；
pruner 配置：`thresholdChars: 8192`、`headChars: 4096`、`tailChars: 1024`。

阈值 = `floor(min(W × 0.25, W − O − 65536))`，W = 1,000,000（`request/context` 声明），得 **250,000**。
实测 11 次压实前的上下文：**248,912 – 252,714，均值 250,645**（偏差 < 1.5%）——机制与实测完全吻合。
触发时刻都是「某一轮的最后一步刚越线、下一轮第一个请求之前」。

形态要点：

2. `shadowedSeqs` 的**首元素恒为上一次压实的替换节点**（#2 的 1564 = #1 的 `compaction/end` seq）→ 这是**滚动摘要链**：每轮重新吞掉上一份摘要。所以「压实已经是增量的」——它永远压最老的连续前缀，保留尾部。
3. 但**摘要调用的输入不是增量的**：每次仍把 shadowed(156k) + 保留尾部(48k) + envelope(15k) ≈ 22 万 tokens 整包送出。

### 2.5 压实的时间与 token 占比

| 口径 | 数值 |
|---|---|
| 压实总墙钟 | 722.1 s = 12.04 min（单次 34.0–100.5 s，均值 65.7 s） |
| 占 turn 累计时长（15.65 h） | **1.28%** |
| 占日历跨度（30.73 h） | 0.65% |
| 占未命中输入 token（6,486,275） | **37.9%** |
| 占输出 token（1,480,665） | 2.7% |
| 压实后首次请求的强制再预填 | 520,877 tokens（cacheRead = 0），是常态步未命中中位数（954）的 **≈49×** |
| 每次顺带重复送的「尾部+envelope」 | 741,334 tokens（11 次累计，纯浪费） |

**结论（Q1）**：压实不是「时间问题」，是「token 结构问题」。墙钟 12 分钟只占 1.3%，但它消耗了 37.9% 的未命中输入，并制造了 0.52 M tokens 的缓存失效再预填。触发阈值 0.25 × 1M 意味着**每 ~195 步就重读一遍全部历史**，而声明窗口还有 75% 没用。

## 5. Q4：流式加载与内存

### 5.1 现在是不是全量解压？——是，而且全量持有

实测四段（同一进程，冷启动）：

| 阶段 | 耗时 | 说明 |
|---|---|---|
| 读 11,835,319 B 进内存 | **5.6 ms** | IO 完全不是瓶颈（占 1.7%） |
| 扫 magic 建 7,673 个偏移 | 2.8 ms | 纯 `indexOf`，可增量维护 |
| 解压 7,673 帧 → 49,639,437 B | **164.9 ms** | 占 49.5% |
| `JSON.parse` 21,285 事件 | **159.6 ms** | 占 47.9% |
| **合计（全量回放）** | **333 ms** | 峰值 RSS **229 MB**，heap 仅 10 MB（事件用完即弃） |
| 对照：分块流式（1 MB chunk，不持全文） | **128.7 ms** | RSS **138 MB**（-40%） |

结论：**96.4% 的时间花在解压+解析，不在读**；RSS 由「同时持有 49.6 MB 解压串」决定（`raws[]` 全留）。分块流式可把 RSS 降 40%，但当前实现是「整文件读 + 全帧解压」。

### 5.2 事件尺寸极度长尾（决定了外置策略的收益）

| 事件尺寸档 | 事件数 | 字节 | 占比 |
|---|---|---|---|
| <1 KB | 14,046 | 6.30 MB | 13.3% |
| 1–4 KB | 4,505 | 8.99 MB | 19.0% |
| 4–16 KB | 2,135 | 16.51 MB | 34.9% |
| **>16 KB** | **599（2.8%）** | **15.52 MB** | **32.8%** |

**599 条事件 = 32.8% 的字节**。把它们外置成 blob 引用，日志立减 15.5 MB，而事件索引反而更干净。

### 5.3 续接一个 21k 事件的会话：三档成本

| 档位 | 需要读 | 需要解压 | 事件数 | 耗时 | 前提 |
|---|---|---|---|---|---|
| **A 现状：全量** | 11,835,319 B | 49,639,437 B | 21,285 | 333 ms / RSS 229 MB | 无 |
| **B 帧索引 + 最近检查点** | 3,029,703 B（+ 索引 92 KB） | 3,076,696 B | 1,236（5.8%） | **≈10 ms** | 有 `.idx` + 最近一次 compaction 的 surface 快照 |
| **C 纯尾部 500 帧** | 844,151 B | 3,500,635 B | ~1,300 | 10.3 ms | 只要能定位尾部 |
| 参考：尾部 100 帧 | 192,538 B | 784,670 B | ~270 | 2.5 ms | — |
| 参考：尾部 1 帧 | 5,544 B | 16,154 B | 2 | 0.1 ms | — |

（B 档的「最近检查点」= 第 11 次压实的 `compaction/end`，seq 20,047；其后只有 1,236 事件 / 3.03 MB / 449 帧。）

### 5.4 顺带一个分片依据：turn → 帧组映射是天然的

| 指标 | 数值 |
|---|---|
| 41 轮 → 41 个连续帧组 | 平均 187 帧 / 287 KB |
| 最大组 t37 | 586 帧 / 912 KB |
| 最小组 t6 | 3 帧 / 15 KB |
| 帧是否跨轮 | 会（7,631 帧不含 `turn/end`），但**轮边界在帧序上严格单调**，可在 `turn/start` 处切组 |

### 5.5 可落地的流式/索引方案（按依赖顺序）

1. **帧索引 sidecar（`.idx`）**：每帧一条 `[u64 byteOffset, u32 byteLen]`，7,673 × 12 B = **92 KB**（占会话 0.8%）。写入侧本就知道偏移，直接 append；崩溃后靠 magic 扫描重建（2.8 ms）。读侧从此可以「只读需要的字节区间」。
2. **事件分流（surface vs telemetry）**：本会话 4,489 条 surface 事件（29.92 MB，63.2%）+ 16,796 条纯日志事件（17.40 MB，36.8%）。续接只需要 surface 流 → 直接砍掉 36.8% 的解压量，且 telemetry 可以按天滚动删除。
3. **turn 分片**：`t001.zt … t041.zt` + `manifest.json`（turn → 帧区间/字节区间/firstSeq/lastSeq/字节数）。截断/归档/按需加载都变成按文件操作，单文件最大 912 KB。
4. **检查点快照**：在每次 `compaction/end` 处落一份 surface 快照（≈50k tokens ≈ 200 KB 文本 JSON）。续接 = 最新快照 + 之后的 surface 事件（当前 1,236 事件 / 3.03 MB）→ 解压量从 49.6 MB 降到 ~3.1 MB（**-94%**），耗时 333 ms → ~20 ms。
5. **大事件外置**：>16 KB 的 599 条 → blob 文件 + 事件里留 `{blobRef, sha256, bytes, head2KB}`。日志 -15.5 MB（-32.8%），列表/搜索/回放都不再需要把 93 KB 的 `stream` 数组读进来。

### 6.1 R1：流式回放块（最大单笔，先说为什么安全）

`assistant/message` 占 24.73 MB（52.3% 的日志），其中：

| 组成 | 字节 | 占比 |
|---|---|---|
| `stream`（流式增量：`texts` + `dt` 数组 + block 事件） | 16.12 MB | 34.1% |
| `message` 本体（text / reasoning / tool-call arguments） | 8.16 MB | 17.2% |
| `source.replayState`（provider 签名 + responseId） | 3.07 MB | 6.5% |

`stream` 里的 `texts` 是 `message.content` 的**逐块重复**。若只保留「block 起止 + 每块时间戳 + 总字数」，UI 仍可重建打字机效果（节奏可按 dt 重采样），日志 −16.1 MB。**收益/成本比最高，风险最低**，建议第一个做。

### 6.2 R2：大工具结果外置（含「读了又剪」的浪费）

| 1–4 KB | 525 | 1,140 KB | 49.3% | 原样进上下文 |
| 4–8 KB | 124 | 639 KB | 27.6% | 写文件 + 前 2 KB + 路径（省 ~40%） |
| 8–16 KB | 9 | 97 KB | 4.2% | 写文件 + 前 1 KB + 路径（省 ~85%） |
| >16 KB | 2 | 39 KB | 1.7% | 同上 |

量化：把 ≥4 KB 的 135 条全部外置为「首 2 KB + 文件路径」→ 结果正文 2,313 KB 中约 **775 KB 不进上下文（−33.5%）**，同时日志侧原始文本只存一份（不再有 pruner 的双份 75.3+28.6 KB）。**关键收益不是日志，而是「模型不再为注定被剪掉的内容付 token」**。

### 6.3 R5：压实能否增量？——能，但要分清两件事

| 维度 | 现状 | 可改进 | 量化 |
|---|---|---|---|
| 压哪些内容 | **已经是增量**：每次只压最老的前缀，保留尾部（滚动摘要链，`shadowedSeqs[0]` 恒为上次摘要节点） | 无需改 | — |
| 摘要请求送什么 | **全量**：shadowed 156k + 尾部 48k + envelope 15k ≈ 222k | 只送「shadowed 区间 + 上一份摘要」，尾部不进 prompt | 每次 −63k tokens → 11 次累计 **−741k tokens（−30%）** |
| 多久压一次 | 0.25 × 1M = 250k 触发（每 ~195 步） | 抬到 0.5（500k）：压缩次数 ≈ 5–6 次 | 墙钟 12.0 → ~6 min；输入 2.46 M → ~1.5 M |

风险提示：把阈值抬到 0.5 的前提是 **provider 真能吃 500k**。本会话所有请求的 `maxTokens=384,000`、`contextWindow=1,000,000` 都是**声明值**；实测 11 次全部在 ~250k 触发，没有任何一次撞到 provider 的硬上限报错，所以 500k 大概率可用，但需 1–2 个对照会话验证。

### 7.2 token 口径

- `usage.totalTokens` = 该步真实上下文（prompt + completion），已用 step 1–4 反算验证。
- `inputTokens` = **未命中（未缓存）输入**；`cacheReadTokens` = 命中缓存的输入。二者相加才是 prompt。
- 字符→token 折算统一用 4 char/token（本会话中英混排，实测 75.3 KB 文档 → 18,052 tokens，比值 4.27；10.2 KB 摘要 → ~3,400 tokens，比值 3.1）。
