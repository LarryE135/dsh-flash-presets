## 1. 口径与方法

### 1.1 读取

会话文件是**多帧首尾相接的 zstd**（每次 append 一帧），本机无 `zstd` 二进制、Python 无 `zstandard`：

```js
// /tmp/sesslib.mjs
const buf = fs.readFileSync(path);
const MAGIC = Buffer.from([0x28, 0xB5, 0x2F, 0xFD]);
// 逐帧 Buffer.indexOf 找帧起点 → zlib.zstdDecompressSync(subarray) → 若干行 JSON
```

全程**单遍流式**（`for (const e of events(P))`），不把 47.3 MB 解压正文 / 21285 事件装进内存；中间产物只落聚合结果（`/tmp/audit/*.json`，最大 3.45 MB）。

### 1.2 关键指标定义

| 指标 | 定义 |
|---|---|
| **step 的 LLM 段** | `step/start.time` → 该步 `assistant/message.time` |
| **step 的工具段** | `assistant/message.time` → `tool/result.time` |
| **prompt tokens** | `usage.inputTokens + usage.cacheReadTokens`（= 该次请求实际送入的上下文长度） |
| **只读命令** | 去掉 `cd '…';` 前缀后匹配 `^(sed -n\|grep\|rg\|ls\|cat\|head\|tail\|wc\|find\|fd\|git (status\|diff\|log\|show\|rev-parse)\|du\|stat\|md5sum\|python3 -c\|pwd)` |
| **真冗余** | 同一命令两次执行之间**没有任何** `edit`/`write`/`sed -i`/`git commit`/`cp`，且输出哈希相同 |

> 只读判定对边界（`echo`、`for` 循环）敏感：**严格口径 555 步 / 27.3%**，**宽松口径（含 echo、for）754 步 / 37.1%**。下文主用严格口径，表里同时给上界。

## 3. turn 38 的 20 分钟卡死

### 3.1 逐事件重建

turn 38 起点 `2026-11-15T07:15:30.654Z`，用户消息是两个字"继续任务"。上一轮 turn 37（87.2 min，169 步）刚在 06:49:44 结束，中间隔了 25.8 min 用户空档。

| **+300.07 s** | `assistant/attempt` finish=error | `pi-ai stream idle timeout after 300000ms` / `TIMEOUT` |
| +300.08 s | `llm/retry` #1 | `delayMs=541.9`，`maxRetries=5` |

四次超时的退避分别是 541.9 / 908 / 1868 / 3812 ms —— 指数退避（base 500 ms、cap 10 s、jitter 0.1），退避本身**完全不是瓶颈**（合计 7.1 s）。

### 3.2 成本

- **墙钟浪费 1203 s ≈ 20.1 min**，占 turn 38 的 36.5%（55.3 min），占全会话轮内时间的 2.1%
- **token**：该步是 turn 38 的第一步，prompt = **175 249 token**（`cacheRead 175 232 + input 17`），输出 660。4 次失败尝试各重发同一份 175 249 token 的上下文、**输出 0**：
  - **701 k prompt token 被重复传输**（这 4 次尝试在日志里没有任何 `usage` 记录——因为根本没有 `assistant/message`）
  - 是否计费取决于供应商（多数对"未产生任何 token 的服务端 stall"不计费，但缓存写/读是否计费不确定）
- 若按 98% 缓存命中折算的等效成本：约 **= 会话总 prompt 的 0.22%**

### 3.3 300 s 这个阈值是否过长？—— 判定：**过长，而且量错了对象**

三条硬证据：

1. **4 次超时全部精确落在 300.01 s**（300.07 / 600.63 / 901.55 / 1203.43，各自减去本次请求起点）。说明这 4 次请求**一个字节都没回来**，包括 SSE 注释/心跳/`message_start`。
2. 第 5 次请求**4.92 s 就成功了**、且只产出 1 个 tool-call。说明链路上游当时已经恢复，前 20 分钟纯粹是"对着一个死连接等"。
3. 实现上，`idleWatchdog` 的计时器在 `iterator.next()` **之前**就 arm（`dsh-timeout/lib/index.js:102-121`），所以这 300 s 覆盖了 **连接建立 + 首字节**；它把"连不上/首 token 不来"和"中途停流"混成同一档。

结论：

- 阈值 300 s 对**中途停流**是合理的（长思考时模型确实可能连续几十秒不吐 chunk）；
- 对**首字节（TTFB）**则长了一个数量级——TTFB 场景下 45–60 s 就该判死；
- 更要命的是 `maxRetries=5` 且**没有总预算**：最坏情况 5 × 300 s = **25 min** 全静默。本次是 4 次 + 第 5 次成功 = 20 min。

### 3.4 有没有更早可观测的信号？—— 实测：**日志里没有，全是"事后"的**

逐项核对本会话的日志能力：

| 候选信号 | 本会话是否可观测 | 证据 |
|---|---|---|
| 首 token 是否到达 | ✗ 无事件 | 只有 `step/start` 和 300 s 后的 `assistant/attempt`，中间**零事件** |
| SSE 心跳 / keep-alive | ✗ 未接入 | `watchdog.pulse()` 只在 `dsh-llm-deepseek` 里被调用（`lib/index.js:2207`），**`dsh-llm-pi-ai` 从不调用** |
| 事件流 seq 停更 | ✓ 但只有 300 s 后才看得出 | 300 s 内 `seq` 不增长——可观测但无告警 |
| 请求头/路由 | ✓ `request/header`（全会话仅 32 条） | 每次请求不重发，无法当"请求开始"标记 |
| 重试开始 | ✓ `llm/retry-started` | 但第 1 次重试已经在 300 s 之后了 |

也就是说：**在 300 s 到点之前，日志、GUI、事件流三者都完全沉默**。这不是"阈值太长"一个问题，而是"没有任何早于阈值的探针"。

### 3.5 实现层根因（可直接改）

```js
// dsh-llm-pi-ai/lib/index.js:2106

// 对比 dsh-llm-deepseek/lib/index.js:2205-2207

```

- `DEFAULT_STREAM_IDLE_TIMEOUT_MS = 3e5`（两个适配器都是 300 000，`dsh-llm-pi-ai:952`）
- pi-ai 路径把 `streamIdleTimeoutMs` 从 profile 读入，可配置但**只有一档**
- 重试策略 `["normal",5,[EMPTY_RESPONSE,RATE_LIMIT,SERVER,TIMEOUT,TRANSPORT],500,10000,0.1]`：5 次、base 500 ms、cap 10 s、jitter 0.1，**无总时长上限**

## 5. 失败 → 重跑回路

### 5.1 bash 层：失败很少，且几乎不重跑

| 项 | 值 |
|---|---|
| `job/settled.detail` 退出码 0 | 1564（96.8%） |
| 退出码 1 / 2 | 32 / 13 |
| 退出码 127 / 128 | 1 / 1 |
| `signal: SIGTERM`（主动 kill） | 4（全部带"我要换做法"注释） |
| **失败 job 合计** | **68（4.2%）** |

失败之后下一条 bash 是什么：

| 行为 | 次数 | 判定 |
|---|---|---|
| 立刻重跑**同一条命令** | 3 | 真冗余（可忽略） |
| 换到**同一脚本的另一次调用** | 7 | 半冗余（多半换了参数） |
| **换成别的命令**（读日志/改代码/查状态） | 58 | **正确行为** |

样本：

- `apply_i18n.py patches_mine.json; grep -c unfinished …` → 同一行立即重跑（3 次里的 1 次）
- `fps_probe.py` 失败 → `fps_probe2.py`（换脚本，属迭代）
- 构建失败 → 下一条是 `grep 'error C'` / `sed -n` 读日志（正确）

**所以"失败→立刻重跑同一命令"的恶性回路在本会话几乎不存在（3 次）**。真正的问题是失败信号本身不可靠（见 5.4）。

### 5.2 run_code 层：PTC 自伤，108 次（5.1%）

`tool/result` 里 `Error: code run failed` 前缀共 **108 条**，全部是"PTC 程序自己没跑起来"，而不是 bash 失败：

| 失败原因 | 次数 | 典型文本 |
|---|---|---|
| **`Identifier 'X' has already been declared`** | **57** | `Uncaught SyntaxError: Identifier 'r' has already been declared` |
| 语法/JS 异常（括号不配对等） | 40 | `Expected '}', got '<eof>'`（t2 里连续 4 次） |
| 执行超时（120 s 上限） | 11 | `execution deadline reached (120000ms); retained variables were cleared` |
| **合计** | **108 / 2111 = 5.1%** | |

代价（实测 usage）：

| 项 | prompt | LLM |
|---|---|---|
| 这 108 个失败 step 自身 | 16.2 M | 27 min |
| 紧邻的"修复"step | 16.3 M | 20 min |
| **合计** | **32.4 M（占全会话 10.1%）** | **47 min** |

**根因**：PTC 的 REPL 内核在多次 `run_code` 之间**保留顶层 `let/const` 绑定**（工具描述里明写"持久内核：K.x = 1 这次写，下次调用还能读到"）。模型很自然地写 `const r = await tools.bash(…)`，第二次还用 `r` 就直接 `SyntaxError`。本审计过程中我自己也踩了两次。

**最典型的一次串味**（turn 2，step 80–85，同一件事重试 5 次）：

| step | 代码长度 | 内容 |
|---|---|---|
| 81 | 1750 | 把一个 Python 脚本按行塞进 JS 字符串数组 |
| 83 | 1728 | 同上，失败 `Expected '}', got '<eof>'` |
| 84 | 556 | 砍成 3 行再试 |
| 85 | 231 | 再砍成 1 行 |
| 86 | 1721 | 终于换写法 |

一个"多行脚本怎么嵌进 TS 字符串"的转义问题，烧了 5 个 step ≈ **5 × 150 k = 750 k prompt token**。

### 5.3 "FAILED 191 次"的真相：**不是 191 次失败**

对 `tool/result` 全文做 `/failed/i` 统计：**191 条结果命中、共 293 次出现**。但逐条看内容，构成是：

| 实际构成 | 说明 |
|---|---|
| **`Error: code run failed (exception/timeout)`** | **108 条** —— 就是 5.2 节那 108 次 PTC 自伤，**与 bash 无关** |
| 编译日志里的 `FAILED: [code=2] …obj` | 少数，且多半是模型主动 `cat`/`grep` 日志取证的输出 |
| 源码里的字面量（`SCE_GXM_ERROR_RESERVE_FAILED`、`RET_ERROR(..._FAILED)`） | 少数 |

而**区分大小写**的 `/FAILED/g` 只命中 **5 条结果、13 次**；`error C####` 9 条 30 次、`LNK####` 5 条、`Traceback` 6 条。

**结论：`FAILED 191×` 这个数字 90% 是 PTC 自伤的 `code run failed` 前缀，不是 191 次构建/测试失败。** 拿它当"失败率"会高估 20 倍。真正的构建失败（输出含 `error C####` / `FAILED:`）只有 **20 个 job**。

### 5.4 最隐蔽的一条：**57.2% 的命令把退出码管道吞掉了**

| 项 | 值 |
|---|---|
| 以管道接 `tail` / `head` 结尾的命令 | **923 / 1615 = 57.2%** |
| build 类 powershell 调用中被吞退出码的 | **135 / 162 = 83.3%** |
| 退出码 0 但输出里含 `error C####` / `FAILED:` 的 job | **20**（全部 exit 0） |

`powershell … build.ps1 2>&1 | tail -4` 的退出码是 `tail` 的，永远是 0。于是：

1. `job/settled` 说 `exit code: 0`，DSH 认为成功；
2. 模型只好**再把日志读一遍**（→ 又一个只读 step，又一个 149 k prompt）；
3. 失败信息只能靠肉眼从 `tail -4` 的 4 行里认出来。

这是"只读 step 膨胀"和"构建回路变长"的共同上游原因，也是**最容易修**的一条。

## 6. PTC（run_code）特有的浪费

### 6.1 一次 run_code 里只调 1 个内层工具：**60.5%**

| 内层次数 | run_code 个数 | 占比 |
|---|---|---|
| **1** | **1230** | **60.5%** |
| 2 | 569 | 28.0% |
| 3 | 130 | 6.4% |
| 4 | 57 | 2.8% |
| 5 | 25 | 1.2% |
| 6–9 | 21 | 1.0% |
| 合计 | 2032 | 3246 次内层调用，均值 **1.60** |

（另有 79 次 `tool/call` 没有产生任何派发：其中 20 次代码里连一个 `await tools.` 都没有，其余是编译期失败。）

这是 PTC 模式下最典型的 step 膨胀：**每一层"包一层 run_code"都要求一次完整的 LLM 往返（149 k prompt + 9–13 s）**，而内层工具可能只跑了 0.09 s（中位）。

### 6.2 一条只读命令独占一个 step：555 步 / 78.6 M token

| 项 | 严格口径 | 宽松口径（含 echo/for） |
|---|---|---|
| 步数 | 555（27.3%） | 754（37.1%） |
| prompt | 78.6 M（24.5%） | 106.1 M（35.1%） |
| LLM 时间 | 1.76 h | 2.31 h |
| 工具时间 | 14 min | 15 min |
| **LLM : 工具** | **7.8 : 1** | **9.2 : 1** |
| 其中工具 <1 s | 457 步 / 64.1 M / 1.43 h | 658 步 / 92.3 M / 1.98 h |

参照：全会话纯只读命令（`grep`/`sed -n`/`ls`/`cat`/`git` 等）共 **826 条**，其中 `git status` 79 次、git 查询类 134 次。这些命令 100% 可以合并进一次 `run_code`——模型却平均一条一个 step。

### 6.3 另一头：多内层 step 的效率对照

| 项 | 单内层 step | 多内层 step |
|---|---|---|
| 步数 | 1230 | 802 |
| 平均内层调用 | 1.00 | **2.51** |
| 每步 prompt | 143 k | **158 k**（只多 11%） |
| 每步工具时间 | ≈0 | 5.32 h 总量 |
| 每步 LLM | 11.2 s | 15.0 s |

**多内层 step 用 11% 的额外 prompt 换来了 2.51 倍的内层吞吐。** 这就是"批量化"的量化收益上限。

### 6.4 轮询类（问题不大，但记账要清楚）

| 项 | 值 |
|---|---|
| bash 后台化（返回 `jobId`） | 138 次（8.5%） |
| `job_output` 调用 | 142 次，其中返回 `(no new output) [status: running]` 的 **12 次** |
| "整个 step 只做一次 job_output 且无新输出" | 3 步（0.7 M prompt，0.3 min） |
| `wait_agent` 调用 / 其中超时空转 | 15 / **9** |

→ 轮询本身浪费很小（<1 min），**不是优化重点**。但 `wait_agent` 9 次空转说明"等子代理"这件事没有推送机制。

## 7. 优化建议

> 收益口径：均为**本会话可复算的实测值**，不是外推。墙钟指"轮内 LLM 等待时间"，token 指 prompt token。

| # | 改哪个环节 | 动作 | 预期收益 | 难度 | 风险 |
|---|---|---|---|---|---|
| **R1** | `dsh-llm-pi-ai` 空闲看门狗 | 让传输层字节（SSE 注释/心跳/`message_start`）也 `watchdog.pulse()`，与 `dsh-llm-deepseek` 对齐 | 消除"链路活着但无 chunk"的误判；本会话 4 次全量超时至少可避免 1–2 次 | **低**（约 20 行） | 低：只放宽"有字节"的判定，不放宽"无字节" |
| **R2** | 同上：超时分级 | 拆成 **TTFB 超时 60 s** + **中途停流空闲 120 s**（保留 300 s 仅作极端兜底） | turn 38 从 20.1 min → **≤ 4.2 min**（4×60 s + 退避），省 **≈16 min**；少传 3×175 k ≈ **525 k token** | 中（需区分"首个 chunk 前/后"） | 中：TTFB 60 s 对 175 k 大 prompt 偏紧，建议按 prompt 大小线性放宽（60 s + 1 s/10 k token → 175 k 时 ≈ 78 s） |
| **R3** | 重试策略 | 给 `TIMEOUT` 加**总预算**（如 5 min 或 2 次），连续 TTFB 超时后**换路由/换 provider** 而不是同一路由硬重试 5 次 | 最坏 25 min → **5 min**；本会话省 ≈15 min | 低（策略层加 `totalBudgetMs`） | 低：需至少一个备选 provider（本会话只有 `opencodego`，建议先用 wb-proxy 兜底） |
| **R4** | 可观测 | 新增 `llm/attempt-start`、`llm/first-chunk`（带 `ttfbMs`）、`llm/idle-warn`（阈值 50% 打点）；GUI 显示"等待首 token 1m32s" | 把 20 min 静默变成"1 分钟就知道卡了" | 低 | 低：纯增量事件 |
| **R5** | PTC 运行时：作用域 | 每次 `run_code` 在**独立作用域**（IIFE / 新 vm Context）执行；跨调用状态只保留显式 `K.*` | 消灭 **57 次** `already been declared`，省 ≈**17 min + 8.5 M prompt** | **低**（一次性包一层） | 中：会破坏"跨调用复用变量"的便利，需保留 `K` 逃生口 |
| **R6** | PTC 运行时：语法前置校验 | 提交模型前先 `new Function(code)` 试解析；语法错**本地立即回显**，不消耗一次 LLM 往返 | 拦住 40 次语法错的大部分，省 ≈**15 min + 6 M prompt** | 低 | 低：只做 parse，不执行 |
| **R7** | PTC 提示词/工具面 | ① system prompt 加硬规则"只读探查必须合并进同一次 run_code（≥3 条命令）"；② 提供 `tools.bash({ commands: [...] })` 批量执行；③ `run_code` 描述里给"多行脚本用 `String.raw` / heredoc 模板"范例 | 把 555 个只读 step 压到 ~150 个：省 **≈1.2 h LLM + 55 M prompt（17%）** | 低（提示）/ 中（新工具面） | 中：合并后单次输出变长，需保留分页截断；过度合并会"一失败全丢" |
| **R8** | bash 退出码 | ① 命令以管道接 `tail/head` 时自动前置 `set -o pipefail`（或 PowerShell 注入 `$LASTEXITCODE` 检查）；② `job/settled` 增加结构化 `exitCode` / `durationMs` 字段（现在只有 `detail` 字符串） | 20 个"exit 0 但编译失败"的假成功消失；每次假成功至少省一个"读日志"step（≈150 k prompt / 10 s） | **低** | 低：`pipefail` 会改变部分命令语义，建议仅对 `tail/head` 结尾生效 |
| **R9** | step 合并 | 鼓励/示例化"构建→部署→冒烟"三连写进同一个 `run_code`（PTC 本就支持顺序 await）。当前 **56 处** build→deploy 分处两步 | 省 **60 个 step ≈ 13 min LLM + 8.8 M prompt** | 低（提示+示例） | 低：中间失败定位粒度变粗，建议每段 `console.log` 打点 |
| **R10** | 长任务 | ① soak/bench 默认时长降档（2709 s 的 soak 没有信息增量）；② 提供"job 完成即推送"而非模型轮询 | soak 23 次共 **182.6 min**、deploy 108 次共 **117.8 min**；soak 上限压到 10 min 可省 **≈1.5 h 工具墙钟** | 中 | 中：缩短 soak 会降低"长稳"结论强度，需保留显式长跑开关 |
| **R11** | 压缩 | 11 次压缩平均 62.8 s、共 11.5 min；压缩后首个请求 **1.31 M 未缓存输入**（占全会话未缓存的 20%）。建议压缩后**沿用原前缀**（system + 旧 summary 不动）保住 prefix cache，或把阈值从 ~150 k 抬到 ~250 k（本会话 contextWindow 设的是 1 M，压到 150 k 明显保守） | 压缩次数 11 → ~6，省 **≈5 min + 0.7 M 未缓存输入** | 中 | 中：阈值抬高会加大单次 prompt（每步 +100 k token），需按缓存命中率权衡 |
| **R12** | 日志结构 | `job/registered` 增加 `exitCode`、`durationMs`、`background`；`tool/ptc-dispatch` 记录 `compileOk` | 让"重复/失败/后台"这类审计不必再解压 47 MB 文本 | 低 | 低 |

### 7.1 优先级与组合收益

**第一优先（改动小、纯赚）**：R5 + R6 + R8 —— 三个都是"运行时小补丁"，合计：

- 省 **≈32 min LLM**、**≈15 M prompt（4.7%）**
- 消除 108 次（5.1%）自伤式往返

**第二优先（提示词/示例层，不改代码）**：R7 + R9：

- 省 **≈1.4 h LLM**、**≈64 M prompt（20%）**
- 这是**本会话最大的一块可回收收益**

**第三优先（基础设施）**：R1 + R2 + R3 + R4 —— 针对 20 min 静默：

- 省 **≈16–20 min**，并把"最坏 25 min 静默"变成"5 min 内失败或换路"

**第四优先（长任务与压缩）**：R10 + R11 —— 省 ≈1.5 h 工具墙钟 + 5 min。

**组合上限（不牺牲质量的前提下）**：轮内墙钟 15.65 h → **≈12.0 h（-23%）**；prompt token 320 M → **≈232 M（-28%）**。

### 7.2 不建议做的

| 想法 | 为什么不做 |
|---|---|
| 把重复命令"去重/缓存" | 真冗余只有 3 s；39 条里 37 条前面紧跟着 `edit`，去重会**直接吃掉必要迭代** |
| 给 bash 加"结果缓存"（同命令同输出直接返回） | 会掩盖 R8 的假成功问题，且构建类命令的输出本就不该缓存 |
| 提高 `maxRetries` | 本会话 4 次重试全部拿到同样的 TIMEOUT；加次数只会线性放大静默时间 |
| 把所有超时一律缩到 60 s | 会误杀"长思考 + 大 prompt"的正常请求（本会话 prompt 均值 149 k） |

### 8.2 已知的口径边界

1. **token 是实测**（`usage` 字段），但**108 次失败尝试的 token 不在日志里**（没有 `assistant/message`），只能按"上一步 prompt 长度"推算。
2. **只读命令的判定对边界敏感**（`echo` / `for`），文中同时给了严格 555 与宽松 754 两个口径。
3. **"必要迭代"的判定**用了"两次执行之间是否有 `edit`/`write`/`sed -i`/`git commit`/`cp`"这一代理指标；它会把"改了文件但内容等价"的写入也算作必要（偏保守，低估真冗余）。
4. **工具时间与 job 时间不等**（7.68 h vs 8.79 h）：138 次 bash 后台化，job 在 `run_code` 返回后继续跑，与后续 LLM 时间重叠。
5. 会话首尾时间戳有一个陈旧的 `2026-10-26` 早值（`session` 元数据），真实跨度按 turn 1 起算 = **30.73 h**。
