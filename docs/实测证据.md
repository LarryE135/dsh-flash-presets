## v4 / v4-b 候选否决记录（2026-11-01，headless + WB Proxy，办公基准 v5）

### 三条结论

1. **persona 规则改不动正确性。** 四次实验（v4 n=2、v4-b n=2、n=5、n=8×3）里 Q 与六维度、乃至坏单元格数**逐项相同**——同题无论加不加规则，模型给出的答案一样，只是绕路方式不同。
2. **成本效应不可复现。** 同一题在不同轮次会给出相反的符号（O07：n=2 时 +153%、n=5 时 −33%、n=8×3 时中位 −33% 但均值 +3.8%）；单次重尾 run 可占总量 40% 以上。加规则改变的是轮数分布，方向不可预测。
3. **判定标准要改。** 后续 A/B 应以「轮数分布 + p95 Token + 符号检验」为准，重尾题 n ≥ 5，且总量统计前先剔除离群；只报均值和总量的结论不成立。

## 两批规则 A/B：契约先行 + 长文阅读（2026-11-09，都否掉）

背景：lean-v3 的 Windows 基准（660 次作答）里，编程维度 71.9%，其中 polyglot（Exercism 题族，90 次）只有 30.0%；105 次失败里 63 次是「被测代码异常/断言失败」而不是算法错。据此起草了 v4 候选规则「契约先行」（先列 3–8 行公开契约：签名、返回类型、异常类型、错误消息原文、输出格式），本批实验就是验证它。

**仪器**（都走 WB Proxy、headless、同一模型；题面/测试取自 exercism/python main，判分用题目自带测试）：

|---|---|---|---|
| A 给题面 | instructions.md + 桩文件，7 题 | 5/7（71%） | 未测 |

**结论：没有可测收益，规则否掉。**

- C 仪器两臂 12/12 且 token 相同（27.6k vs 27.6k）—— 规格写清楚时模型本来就照做（返回类型、异常消息原文、行尾换行都照做），规则的前提不成立；

### 压缩阈值：0.25 在我们测过的运行里从未触发（2026-11-09）

机制在 `dsh-compaction-basic` 第 132 行：`thresholdTokens = min(contextWindow × thresholdRatio, pressureBudget)`。桌面/web profile 声明 window = 1,000,000，所以本预设的 0.25 = 250k 才压缩，dsh 默认 0.8 = 800k。

- **全量扫描 109 个 events.jsonl**（v4-bench 32 + poly-ab 31 + longqa 46）的上下文峰值（`inputTokens + cacheReadTokens` 的最大值）：**中位 20k、p90 34k、最大 126,506**；峰值 ≥ 250k 的运行 **0/109**，≥ 800k 也是 0/109。
- 直接把阈值压到 **0.04（40k）** 在 O08 上跑：上下文峰值 39.6k，**一次都没触发**。
- 原因不是模型不读：`tool-result-pruner`（8192 字符 → head 4096 + tail 1024）把每次工具输出压到约 5.2k 字符（≈1.3k token），上下文随步数线性慢涨，250k 需要约 190 次「重」工具调用。

**一处旧读数的更正**：v4-bench 里「10/32 运行超 250k token」是**累计 token**（每次请求 `totalTokens` 求和，含 cache 读），最高一条 4,917,515 是 166 步累出来的；同一条运行的上下文峰值只有 126,506。以前把「累计 token」当「上下文大小」用，属于口径混淆。

顺手测了真正起作用的旋钮（O01，n=4）：pruner 8192/4096 对 2048/1024 —— 每次 token 中位 **297k vs 228k**（约 -24%，8k 臂第 4 次是 104 步的抖动离群）。但 office 床的 Q 在 8 次里全是 68.9167，没有分辨力，所以这只能算成本现象；n=4 方差大，不足以下发布结论。

复现：`bash $HOME/Work/compact-bench/run.sh <c04|c10|c25|c80|p2k|p8k> <O01..O08> <rep>`（阈值臂与 pruner 臂都在 `$HOME/Work/v4-bench/overlays`）。

**pruner 也不是免费的降本旋钮**（两处结果相反）：

| 床 | 8192/4096 | 2048/1024 | 说明 |
|---|---|---|---|
| office O01（n=4） | 中位 297k token | 中位 228k token | 结构化交付、少量大读，截断省钱 |
| LongBench lb2 8 题（n=1） | 中位 66.9k token，2/8 | 中位 83.9k token，2/8 | 截断后要反复重读，反而更贵，准确率不变 |

结论：保留 shipped 的 8192；要动它必须按工作负载验证（长文读的任务会反向受益）。
