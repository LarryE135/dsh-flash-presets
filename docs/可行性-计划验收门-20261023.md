# 可行性：用「计划 + 验收门」压住过早收工

日期 2026-10-23｜依据：用户提供的 3 份真实会话（同一道 Three.js 樱花树题，同渠道）

## 1. 三份会话的对比

| 会话 | 交互过程 | 步数 | 工具调用 | 验收命令 | 收工方式 |
|---|---|---|---|---|---|
| `99f92018` | 一次给全需求，直接开工 | 40 | 37 | **0** | 截图迭代后自述"已完成，通过渲染/交互/性能验证" |
| `d8664c68` | 一次给全需求，直接开工 | 45 | 43 | **0** | 截图迭代后自述"已完成，无头 Chrome 实测通过" |
| `4109efc1` | 先出计划 → 用户回"**标准更高一点**" → 重做计划 → "开始执行" | **92** | 90 | **27 次**（`node tools/verify.mjs`、`npm run verify`） | 写了验收脚本，逐项断言后交工 |

三份用的是同一条需求（15 条 bullet），需求本身**完全相同**。

## 2. 结论：起作用的是"可判定的验收项"，不是 plan mode 本身

- 会话 3 的计划**第一次就被用户否掉了**（"标准更高一点"）。真正的转折点是那句反馈逼出了一份**编号验收清单**，进而催生 `verify.mjs`（模型不变量、暂停、回收、滑杆、性能指标断言）。
- 前两份会话没有任何自动化验收：全部证据止于"我截了图，看起来对"。
- 因此单纯加"计划"这一步不足以改变行为——**计划里必须包含可被命令判定的验收项**，否则计划只是多写一段话。

需求里那句"完成前可以反复检查，**直到足够让人满意为止**"正好是失效点：**"足够满意"没有判定标准**，模型只能自己给自己发合格证。

## 3. 可行的改法（additive，不动 v3）

新文件 `presets/flash-lean-ptc-v4-plan-accept.patch.yml`，三条规则：

1. **立标**：开工前把需求逐条转成编号验收项写入 `ACCEPTANCE.md`，每项必须能被命令或截图判定；含糊的表述要改写成可判定形式。
2. **升一档**：写完自评一次"这份标准够不够高"，把"能用/看起来对"升级为"可测的阈值"（仿用户那句"标准更高一点"）。
3. **停止闸门**：交付前逐项取证（跑验收脚本/截图/读数）；**没有证据的项不得声称完成**，未完成项必须显式列出。

触发条件（防止简单任务被拖长）：需求条目 ≥5 条，或出现"直到满意/做到最好/自行发挥"这类开放标准时才启用；否则按 v3 原样跑。

与 plan-mode 插件的配合（可选）：`dsh-plan-mode` 支持配置 `section`，把它配成"计划必须包含验收清单与判定命令"，用户 `/plan` 时自动生效，不必改 v3。

## 4. 风险

| 风险 | 估计 | 缓解 |
|---|---|---|
| token 上升 | +50%~120%（92 步 vs 40 步） | 触发条件限流；验收脚本本身很便宜 |
| 简单任务过度触发 | 中 | 需求条目计数门控 |
| 与 v3 的 lean 目标冲突 | 中 | 作为**独立候选预设**，不并入 v3 |
| 验收项写成空话 | 高 | 规则要求"每项必须附判定命令"，否则视为未立标 |

## 5. 验证方案

- 任务：同一道樱花树题（需求可枚举，且原句带开放标准）
- 臂：v3 基线 vs v3+v4-plan-accept，各 8 次，WB Proxy
- 指标：步数、验收命令次数、验收项覆盖率（脚本核对 + 人工评分 1–10）、billed token、峰值上下文
- 判定：覆盖率与评分显著上升，且 token 增幅 < 2× 才算通过

## 6. 建议

先做 v4 候选文件并跑 8+8 对照。**不要**只往 v3 里堆强调话术——三份会话说明 v3 的规则并不缺，缺的是"可判定的完工条件"和"没证据不许收工"这道闸门。
