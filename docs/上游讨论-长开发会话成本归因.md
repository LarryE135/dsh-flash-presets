# 长开发会话的成本归因（DSH 0.2.2-rc.3 实测）

> 数据来源：一个真实会话（41 轮 / 2,152 步 / 2,111 次 `run_code`，wall clock 15.65 h）。
> 会话文件 `session.v4.jsonl.zstd` 为**多帧首尾相接**（7,673 帧 / 11.83 MB / 解压 49.64 MB / 21,285 事件），
> 本文全部统计由 Node 逐帧流式解压得出（`zlib.zstdDecompressSync` + 帧切分），未改动会话文件。
> 复现脚本：`/tmp/sesslib.mjs`、`/tmp/analyze-session.mjs`、`/tmp/audit/*`（子代理审计）。

## 一句话结论

**钱不是花在重试上，是花在「步数 × 上下文重发」上。** 重试只占 2%，压实的墙钟只占 1.3%；而 27.3% 的步只跑了一条只读命令，每步重发平均 149k prompt token（98% 命中缓存，但基数 ×2,152 步 = 320 M）。

## 一、总盘

| 指标 | 数值 |
|---|---|
| 轮次 / 步 / `run_code` | 41 / 2,152 / 2,111 |
| wall clock（逐轮累计） | 15.65 h（跨度 30.73 h，49% 轮间空闲） |
| prompt 重发 | **320.2 M tokens**（98% 缓存命中）= 活上下文的 **187×** |
| 写入正文 | 6.57 MB（reasoning 35% / 工具结果 34% / 工具参数 29% / 可见文本 1%） |
| bash 执行 | 1,615 job / 527 min（8.8 h）/ 平均 19.6 s |
| 压实 | 11 次 / 墙钟 722 s（**1.28%**）/ 摘要输入 **2.46 M token（占未命中输入 37.9%）** |
| LLM 重试 | 4 次，全在 turn 38 |
| `run_code` 失败 | 120 / 2,122（5.7%） |

## 二、四个可修的浪费点

### 1. 一步一动作（最大头）

- `run_code` 平均只做 **1.54** 个内层动作；**60.5% 只做 1 个**。
- **555 步（27.3%）只跑一条只读命令**，吃掉 78.6 M prompt（24.5%）+ 1.76 h LLM，而工具本身只跑 14 min（**7.8 : 1**）。
- 对比：重复命令只多跑 144 次、26.3 min（2.8%），真冗余 2 条 3 秒；bash 并行重叠 254 次只省 5%。**这两条都不值得优化。**

### 2. 重试的形态问题：没有早于阈值的探针

- turn 38：4 次尝试全部**精确 300.01 s、零字节返回、无 SSE 心跳**，第 5 次 **4.92 s** 成功 → 上游早已恢复。
- 代价：**20.1 min + 701 k prompt token**，日志/GUI 全程零事件。
- 根因：`DEFAULT_STREAM_IDLE_TIMEOUT_MS = 3e5`；`watchdog.pulse()` 只在 `dsh-llm-deepseek` 接线，**pi-ai 通道从不调用**；`maxRetries=5` 无总预算 → 最坏 25 min。
- 300 s 对「首字节」过长（45–60 s 够），对「中途停流」合理 —— 缺的是**两段超时 + 传输层 heartbeat**。

### 3. PTC 自身的编译/重声明失败

`run_code` 的 120 次失败分解：

| 类型 | 次数 | 占比 |
|---|---:|---:|
| **REPL 重声明**（`Identifier already declared`） | 57 | 47.5% |
| 内层工具报错（`Uncaught:…`） | 21 | 17.5% |
| 语法错误（`Expected ',' / '}' / ';'`） | 18 | 15.0% |
| `run_code` 超时 | 11 | 9.2% |
| 其它（python traceback 等） | 13 | 10.8% |

- **68% 的 `run_code` 含顶层 `let/const/function/class`** → 跨调用撞名是结构性问题，不是模型偶然手滑。
- 语法错误只有 18 次（0.9%）→ **「提交前语法预校验」收益很低**（我实测用同一套 `stripTypeScriptTypes`+`vm.Script` 只能拦 0.9%），这条路不划算。
- 真正的修法是**运行时把重声明当覆盖**（或每次程序自动块级作用域 + 显式持久化 API），可省 57 次往返 ≈ 8.5 M prompt / ≈25 min。

### 4. 上下文工程：读了全部只留四分之一

- 压实后 cache=0，**强制再预填 520,877 tokens**；阈值 0.25 的实测触发点 248,912–252,714。
- `prune` 的 shadowedRange 全是退化区间 `[k,k]`；被剪的正是 5 份盘点文档（22.9/16.0/13.7/12.3/10.5 KB → 各 ~5.7 KB），**读 100% 留 24%**，日志里还双份存了 46.7 KB。
- 大工具结果直接进上下文：最大 21.7 KB（整份 HANDOVER）、17.4 KB（源码片段）。
- **≥4 KB 结果外置**（文件 + 前 2 KB + 路径）可让结果正文 −33.5%，并消灭「读了又剪」的 775 KB。

## 三、存储/续接（与「流式加载、内存」直接相关）

| 观测 | 数值 |
|---|---|
| 回放一次全量会话 | 333 ms / RSS 229 MB，**96.4% 在解压+解析** |
| 检查点续接（449 帧 / 3.03 MB / 1,236 事件） | **10 ms（−94%）** |
| 大事件 | 599 条 >16 KB，占字节 32.8% |
| 帧结构 | 7,673 帧，各自独立可解压（实测逐帧解全部成功） |

`dsh-session-persistence-jsonl` 已有多帧复用的原生解码器（`privateZstdStream`），但**仍从头顺序解码**，因为**没有帧索引**。加一个 `.idx`（帧偏移 → 首 seq，约 92 KB）可把续接从 O(全文件) 降到 O(尾部)。

## 四、建议（按收益/成本）

| # | 动作 | 层 | 预期 | 难度 |
|---|---|---|---|---|
| 1 | 只读探查合并、构建→部署→冒烟不拆步、禁用 `\| tail/head` 吞退出码 | 提示/预设 | −20% prompt、−1.4 h | 低 |
| 2 | 重声明当覆盖（或块级作用域 + 持久化 API） | PTC 运行时 | −57 次往返 ≈ −25 min / −8.5 M | 中 |
| 3 | 传输层 heartbeat + TTFB 60 s / 停流 120 s + 总预算 | pi-ai | 20 min 静默 → ≤4 min | 中 |
| 4 | ≥4 KB 工具结果外置 | 上下文 | 结果正文 −33.5% | 中 |
| 5 | 压实增量（只送 shadowed 区间 + 上一份摘要）、阈值 0.25→0.5 | 上下文 | 输入 −30%、11→5~6 次 | 低 |
| 6 | 会话分层 + 帧索引 + 检查点 | 存储 | 续接 333→20 ms、解压 49.6→3.1 MB | 中高 |
| 7 | 流式回放块正文化（16.12 MB = 34.1% 字节） | 存储 | 日志 47.3→14 MB | 低 |

组合上限（不牺牲质量）：**wall clock 15.65 h → ≈12.0 h（−23%），prompt 320 M → ≈232 M（−28%）**。

## 五、口径与边界

- 全部为**单会话**观测（41 轮、Vita3K 模拟器开发），不宣称普遍性；比例类结论（步数驱动 > 重试驱动）对长会话应稳健。
- token 数来自会话内 provider 记账（缓存命中/未命中分开），不是账单。
- 「165 条 stat 风暴 ≈20 ms」「0.12 ms/次」等微基准属于原会话自带的现场证据，本文只引用不复算。
