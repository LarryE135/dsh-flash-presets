# 架构改进：把 run_code 的固定开销从"每次买单"改成"一次买单"

> 背景：`run_code` 折叠调用能省步数，但短任务里反而更慢。阈值（"3 次以上才折叠"）是软约束，
> 本文记录的是**架构层**的两项改动——把固定成本抹掉，而不是让模型自己判断值不值。

## 1. 实测：固定成本到底在哪

| 测量 | 数值 | 含义 |
|---|---|---|
| 嵌套 `bash echo` 单次 | 44 / 42 ms | 每次嵌套调用的通道 + 调度开销 |
| 嵌套 `bash sleep 0.2` | 242 ms | 44 + 命令本身 200 |
| 3× `bash sleep 0.2` + `Promise.all` | 734 ms | ≈ 3×242 → **被串行化**，没有并行 |
| 3× `glob` + `Promise.all` | 125 ms | ≈ 3×41 → 只读工具同样串行 |
| 单次 `read` | 6 ms | 轻工具几乎零开销 |
| **program 内进程 uptime** | **108 ms** | 每个 program 冷启 node + 装载运行时 |

三条结论：
1. **每个 program 交一次 ~108 ms 冷启动税**（node + 运行时装载）；
2. **program 内部的"并行"是假的**——`dsh-tools` 只对 `isConcurrencySafe() === true` 的工具开并发，
   `glob`/`grep` 没声明，于是被当作 exclusive 串行执行；
3. 因此折叠只省**模型步数**（每次全前缀重读），不省工具墙钟。

## 2. 改动 A：给只读工具补并发声明（**对原生多调用有效，已恢复**）

> **两次实测，结论要分开看：**
> - **run_code 的嵌套调用**：无效。同一个 program 内 4 个相同 `glob`，`Promise.all` 97 ms vs 顺序 106 ms。
>   嵌套调用走 PTC 自己的 JSON 通道，不查这个标记。
> - **模型在一步里发多个原生 tool call**：**有效，且是 2.4×**。见 §3.6 的时间线。
>
> 因为后者才是"折叠之外"的真实场景，补丁已重新装回 web/headless 两个 profile。


`dsh-tool-fs-search` 的 `glob` / `grep` 没有 `isConcurrencySafe`。补丁：

```js
name: "glob",
isConcurrencySafe: () => true,  // 本地补丁：只读工具，允许同一步内并行
```

- 落点：`~/.dsh/profiles/{web,headless}/node_modules/@deepseek-ai/dsh-tool-fs-search/lib/index.js`
  （全局安装不动，root 所有）；
- 生效：重启进程；
- 回滚：删掉 profile 内的副本，回到全局原版；
- 预期：3 路 `glob` 从 ~125 ms 降到 ~45 ms；`grep`/`read` 混合批同样受益。

## 3. 改动 B：PTC 运行时改为常驻（已写入配置，待重启验证）

运行时本来就是两档：`executionMode: "per-call" | "persistent-in-memory"`（默认 per-call，
`dsh-ptc-runtime-node/lib/index.js:692`）。改成常驻后，program 在**同一个 node 进程**里跑 REPL：

```yaml
- id: ptc-runtime
  config:
    executionMode: persistent-in-memory
```

- 收益：每个 program 省掉 ~108 ms（node 启动 + 运行时装载），连续几十个小 program 时收益线性累积；
- 代价：① 同一 state owner 不能并发跑 program（本来也是串行）；② 进程内变量会跨 program 残留，
  需要"干净环境"的脚本要自己重置；③ 进程崩了影响该会话的运行时（per-call 模式下只影响当次）；
- 回滚：删掉这 3 行配置（备份 `cordis.patch.yml.bak-before-persistent-*`）。

## 3.5 实测结论（2026-11-03，重启后）

| 改动 | 结果 | 证据 |
|---|---|---|
| **B 常驻** | **✅ 生效** | 连续 4 个 program 的 `process.pid` 全是 **293396**，`uptime` 从 186 ms → 18.4 s 递增 |
| **B 副作用** | 变量跨 program 残留 | 第 2 个 program 里 `const t0` 直接报 `Identifier 't0' has already been declared`；`globalThis` 计数跨 program 累加 |
| **A 并发** | **❌ 对嵌套调用无效** | 同一个 program 内 4 个相同 `glob`：`Promise.all` **97 ms** vs 顺序 **106 ms**（≈无差别） |

结论：
1. **B 成功**，每 program 省掉约 108 ms 冷启动；代价是"REPL 语义"——变量/模块状态在 program 之间保留，
   重名变量会直接报错，写 program 时要么用唯一名，要么包一层 IIFE。
2. **A 不生效**：`isConcurrencySafe` 只被 agent-loop 的 parallel 调度器消费（`dsh-tools/lib/index.js:3157`），
   而 run_code 内部的嵌套调用走的是 PTC 自己的 JSON 通道，仍然串行。**它要等 C（模型一轮发多个原生
   tool call）才有意义**。当前保留它零成本、但不要宣称收益。

## 3.6 C 已确认：模型确实会在一步里发多个 tool call（2026-11-03）

pipeline：`dsh --json` 输出经时间戳打标后解析，取 step 1 的时间线。

```text
plain（无补丁，glob 未声明并发）
  +    0 ms  step_start
  + 2027 ms  tool_call:glob
  + 2265 ms  tool_result        ← 一个跑完才发下一个
  + 2265 ms  tool_call:glob
  + 2394 ms  tool_result
  + 2394 ms  tool_call:glob
  + 2519 ms  tool_result
  + 2519 ms  step_end           → 工具段 492 ms

patched（glob/grep 声明 isConcurrencySafe）
  +    0 ms  step_start
  + 1802 ms  tool_call:glob
  + 1803 ms  tool_call:glob     ← 三个同时发出
  + 1804 ms  tool_call:glob
  + 2004 ms  tool_result
  + 2006 ms  tool_result
  + 2008 ms  tool_result
  + 2008 ms  step_end           → 工具段 204 ms
```

- 三个调用由**模型在同一 assistant 消息里发出**（provider 支持 parallel tool calls，已确认）；
- agent-loop 的 parallel 调度器按 `isConcurrencySafe` 放行 → 工具段 **492 → 204 ms（2.4×）**；
- 与 run_code 折叠的关系：折叠省**步数**（整段前缀重读），原生多调用省**工具等待**，两者正交，可以叠。

## 3.7 复核（2026-11-03 晚，三项改动全部在位）

| 指标 | 改前 | 改后 | 倍率 |
|---|---|---|---|
| 每 program 冷启动 | 108 ms（`process.uptime()` 首行） | 0（pid 10825 恒定，uptime 递增） | — |
| 嵌套 `bash` 单次 | 44 ms | **16 ms**（5 次中位：16/18/16/14/16） | **2.75×** |
| 原生 3 路 `glob` | 492 ms（串行：call→result→call→result→call→result） | **204 ms**（call×3 → result×3，实测时间线） | **2.4×** |
| 抛异常后 REPL | 未测 | **存活**：抛出后同一 pid 继续可用（uptime 75.9 s） | — |

仍未量化：`run_code` 折叠相对"直接调用"的 token/墙钟 A/B（需要按任务规模分层）。

## 4.5 运维坑（2026-11-03 实际踩到）

用脚本"截断到某个注释标记再追加"的方式改 `cordis.patch.yml`，会**静默吞掉标记之后的所有块**——
本次就是这样把 $PTCRUNTIME 的 `executionMode: persistent-in-memory` 删掉了，重启后 `run_code` 又回到
per-call（`process.uptime` = 101 ms 即冷启），直到复查发现。

规则：改这个文件只能**按 YAML 结构增删单个条目**，或"追加到文件末尾"；任何基于行号/标记的截断都要先 diff。

## 6. 一句话

> 固定开销不是靠"少用"来省，是靠**让它只付一次**：进程常驻 + 只读工具并发。
> 阈值仍然留着，但它从"主要手段"降级成"兜底"。
