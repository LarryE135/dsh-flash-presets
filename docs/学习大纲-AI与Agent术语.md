## 1. L0 · 推理与计费（最容易被问倒的一层）

### 1.1 基本单位
| 术语 | 一句话定义 | 与本插件的关系 |
|---|---|---|
| token | 模型的最小计费/处理单位；中英混排约 1 token ≈ 0.6–1.5 汉字/4 英文字符 | 所有预算都按 token 算，不是字符 |
| context window | 单次推理能容纳的 token 上限（输入 + 输出） | 超过就要 compaction，插件的一部分设计就是为它省额度 |
| prompt / prefix | 本次请求被送进模型的全部内容；"前缀"指与上一轮完全相同的开头部分 | 每个 step 都要重读整个前缀，这是成本主项 |
| completion / output | 模型这一轮生成的内容 | 单价最高的一档 |

### 1.2 prefill 与 decode
- **prefill**：把整段输入一次性并行算完（算力密集），决定"读得多快"；
- **decode**：逐 token 串行生成（显存带宽密集），决定"写得多快"；
- **KV cache**：prefill 产生的中间状态，缓存后可复用 → 这是"前缀缓存"的物理基础。

### 1.3 前缀缓存（prefix cache）
| 术语 | 定义 | 关键性质 |
|---|---|---|
| cache hit | 本次请求的前缀与历史命中，按便宜的缓存价计费 | 只认**完全一致的前缀**，改一个字就失效 |
| cache miss | 未命中部分按输入价（P_in）计费 | 新工具结果、新用户消息都是 miss |
| P_cache / P_in / P_out | 缓存读价 / 输入价 / 输出价，通常 P_cache < P_in ≤ P_out | 我们的成本公式三件套 |
| TTL | 缓存存活时间，过期重算 | 长思考/长等待后前缀可能已失效 |

### 1.4 三个必背公式
```
单步成本 ≈ prefix × P_cache + new × P_in + out × P_out
截断收益 ≈ 后续步数 N × 被裁 token 数 × P_cache   ← 收益是"每步都少读"
取回成本 ≈ 1 × (prefix × P_cache) + 小输出 × P_out  ← 成本是"一次性"
判断式：N × 被裁(token) × P_cache  >  (prefix × P_cache + 取回输出 × P_out)  ⇒ 值得裁
```
**这一层就是"裁切值不值"的全部算术**，能当场写出这三行，你就不会被绕进去。

## 2. L0 · Agent 循环（本插件的舞台）

| 术语 | 定义 | 注意 |
|---|---|---|
| turn（回合） | 一次用户输入到助手交付 | 一轮里可能有多个 step |
| step（步） | 一次模型推理 + 它发起的所有工具调用 | **每一步都重读整个前缀** |
| tool call | 模型请求执行外部动作（bash/read/grep/write…） | grep 也是 tool call —— 这是关键 |
| tool result | 工具回传的内容，随后进入下轮前缀 | 大结果会长期抬高 prefix |
| agent loop | model → tool → result → model 的循环 | 循环里没有"零成本动作" |
| 编排 / orchestration | 决定何时调用、如何切分任务 | plan mode 属于编排层 |

## 3. L0 · 上下文管理（本插件的核心战场）

| 术语 | 定义 | 我们怎么用 |
|---|---|---|
| truncation（截断） | 工具**内部**限流，超限部分丢弃/落盘（如 bash 8 KB） | 有路标：`full output: <path>` |
| pruning（裁剪） | 对**已生成**的工具结果事后改写（pruner：留头尾、删中段） | 我们给它补了中段落盘 |
| spill（溢出文件） | 被移出上下文的内容落到磁盘 | 可 grep / 区间读，**可寻址** |
| addressable（可寻址） | 丢掉的东西还留了定位信息（路径 + 偏移） | "无损"的严格定义 |
| compaction（压缩） | 历史过长时把旧回合摘要化 | **不可寻址**，真丢 |
| context rot / 稀释 | 无关内容过多导致注意力下降 | 裁剪的隐性收益 |
| 结构化结果块 | 工具结果可以是 text 块，也可以是结构化块（如 `lines:[]`） | pruner 只统计 text 块 → read 不触发 |

**必背区分**：截断（工具层、主动、有路标）／裁剪（会话层、事后、原本无路标）／压缩（历史层、不可逆）。

## 4. L1 · 计划与状态（plan mode 与 todo）

| 术语 | 定义 | 我们的实现 |
|---|---|---|
| plan mode | 先出计划、经批准再执行的交互模式 | 原生 policy 段 + 审批门 |
| approval gate | 执行前的确认关卡（无头环境没有通道 → 会卡死） | `DSH_PLAN_MODE_UI_HEADLESS` 三态 |
| native 判定 | 判断"当前是否由原生 plan mode 接管" | 投影 → 服务 → 簿记 三级链 |
| 状态投影（projection） | 从事件流推导出的只读状态 | 判定第一优先级 |
| 簿记状态（bookkeeping） | 自己维护的开关/缓存 | 第三优先级，需同步 |
| todo list | 结构化任务清单（pending/in_progress/completed） | 必须**逐项**推进 |
| stale list | 只在结尾一次性打钩的坏清单 | 提示词正是治它 |
| 幂等 / 竞态 | 重复触发不产生副作用 / 时序导致错判 | 重启首请求竞态就修过 |

| 术语 | 定义 | 教训 |

## 7. 12 个"会被抓"的点（每个准备一句反驳）

| # | 对方的话 | 你的回应要点 |
|---|---|---|
| 1 | "grep 不用 tool calling？" | grep **就是** tool call；省的从来不是调用次数，是**输出体积** |
| 2 | "裁切省了一次调用" | 不成立：裁切省的是后续每步都要重读的那段前缀 |
| 3 | "pruner 无损吗" | 有路标才无损；**补丁前会丢**，这点我认 |
| 4 | "落盘等于把问题挪到磁盘" | 是挪，但挪完**可寻址**；不可寻址才是真丢 |
| 5 | "compaction 也能取回吗" | 不能。它摘要化，不可逆；别把三者混为一谈 |
| 6 | "多花的检索不也是钱" | 是，一次 step 的前缀成本；所以判断式要算 N 步收益 |
| 7 | "上下文大就多给嘛，4k→8k→16k" | 每步都要重读，涨价是**乘步数**的；给容量不等于给可用性 |
| 8 | "n=1 就能看出来" | 方向性结论至少要 n≥3 + 中位数，否则等于抽样噪声 |
| 9 | "两个版本差不多" | 先问被测版本与路径（我们的坑：符号链接指向 0.5.2） |
| 10 | "计划模式不就是让人看一眼" | 它是**审批门 + 状态机**，无头环境没有通道就会死锁 |
| 11 | "todo 列表是装饰" | 它是外部化的工作记忆；只在结尾打钩的列表等于没有 |
| 12 | "你的数字怎么来的" | 报：判分器条目、n、中位数、对照臂、以及**哪些没验证** |

## 9. 三句话版本（最终要背下来的）

1. **成本**：每一步都要重读整个前缀，所以省钱的主战场是"别让上下文里长期躺着大块数据"。
2. **机制**：截断分三层——工具层限流（有路标）、会话层裁剪（我们补了落盘）、历史层压缩（不可逆）。
3. **代价**：取回要一次工具调用，前缀成本不减，省的是**输出体积**与"重跑又超限"的不确定性。
