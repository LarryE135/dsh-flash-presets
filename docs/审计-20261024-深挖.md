# 深挖审计（2026-10-24 · 第二轮）

第一轮看的是「有没有」和「对不对」，这一轮换了个问法：**这些检查真的会拦住错误吗？** 方法是对着检查脚本做变异测试——往仓库里注入 11 类破坏，看哪些被抓住、哪些漏网。

## 核心结论：三个检查是空的

| # | 发现 | 严重度 | 处理 |
|---|---|---|---|
| 1 | `npm run verify` 的**取值断言全部被跳过** | 高 | 已补仓库层断言 |
| 2 | `.gitattributes` 声明 `*.ps1` 为 CRLF，**实际文件是 LF** | 中 | 已统一为 LF |
| 3 | 文档里的相对链接**没有任何检查** | 中 | 已加死链检查 |
| 4 | 规则矛盾检测**只查单向**（禁用在前） | 低 | 已改双向 |

## 1. 取值断言是空的（最严重）

`scripts/verify-presets.mjs` 里对 `order`、`thresholdRatio`、`retainTokens`、规则条数的断言全部写在：

```js
if (!repoOnly) {   // ← 安装层，--repo-only 时整段跳过
```

而 `npm run verify` 用的正是 `--repo-only`。后果：

- 把 v3 的 `thresholdRatio: 0.25` 改成 `0.5` 并重新合成 → `npm run verify` **全绿**
- 把预设 id 从 `flash-lean-ptc-v3` 改成 `flash-lean-ptc-vX` → 同样全绿

CI 因为有真实安装步骤（不带 `--repo-only`）才挡得住，但**本地发布前守卫等于没设**。已补一段直接读 `presets/*.patch.yml` 的仓库层断言（每个预设 10 项）。

## 2. 行尾声明与事实不符

`git ls-files --eol scripts/install.ps1` 输出：

```
i/lf  w/lf  attr/text eol=crlf   scripts/install.ps1
```

索引是 LF、工作区是 LF，但属性声明是 CRLF——三者不一致。PowerShell 5.1 与 7 都能读 LF，所以把声明改成 LF，并新增**以 .gitattributes 为准**的双向行尾检查（`eol=lf` 的文件不许有 CR，`eol=crlf` 的必须有）。
