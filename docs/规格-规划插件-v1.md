# 规格：规划插件（plan-probe）v1

状态：草案（未提交）　｜　依据：七个样例、60+ 次实现（每臂 n≥5）、Welch t 检验

## 1. 目标

把「开工前的规划核查」做成插件能力，解决三件事：

1. **档位**：默认不规划；需要时用轻量档；任务含未知项时升全量档。
2. **作用域**：规划协议只注入首轮，还是每轮都注入。
3. **可验证**：规划产物必须是**可执行清单**，不是散文。

非目标：不做多轮自我评审（那是 `plan-rounds` 的职责）、不做跨会话记忆、不改 DSH 内核。

## 2. 概念模型

```
档位 tier   : off | light（v2） | full（v3）
作用域 scope: first（仅首轮） | always（每轮）
两者正交：tier 决定产出什么，scope 决定注入多久。
```

| 档位 | 产物 | 规划成本（实测区间） |
|---|---|---|
| off | 无 | 0 |
| light | CONVENTIONS.md / AMBIGUITIES.md / P0-EXEC.yml / P1-TARGETS.yml | 55–75k |
| full | EVIDENCE.md（带 ✅/👁/🤷 标记）+ 上列四份（P0 每条带 source） | 60–90k |

实测参考：缩略图任务 light 64.4k / full 60.1k（full 反便宜，因为省掉“纠结往哪写”）；
改写任务 light 63k / full 90k（full 贵 43%）；并发任务 light **两次都无产出** / full 88k。

## 3. 档位判定（路由器）

按顺序问，命中即停：

| # | 问题 | 命中 → |
|---|---|---|
| Q1 | 需求里有**并发、时序、限流、超时**这类“不跑起来看不见”的约束吗？ | **full**（light 会空转，实测 2/2 失败） |
| Q2 | 有**不可信的外部契约**（文档过期、库版本、CLI 参数、接口形状）吗？ | full |
| Q3 | 有**规模或数量的隐含要求**（10 万行、32 MB、1000 条）吗？ | full |
| Q4 | 主要验收对象是**像素 / 手感 / 布局**吗？ | light |
| ~~Q5~~ | ~~被改的代码就在眼前 → off~~ | **已删除**：实测 off 3/5、light 5/5，代价仅 +2k |
| 默认 | 其余情况 | **light** |

路由只影响**第一轮的档位**；跑起来后触闸（见 §6）允许升级，**不允许自动降级**。


### 3.1 谁来定档（自动为主，手动可覆盖）

| 机制 | 规则 |
|---|---|
| 默认 | tier=light、scope=always（写进 Config 默认值） |
| 自动升档 | 命中任一信号：①第 1 轮结束磁盘无新产物 ②触步数/墙钟闸 ③同一命令重复 >=3 次。**最多升一次**（light→full） |
| 手动覆盖 | /plan-tier off | light | full，优先级最高，覆盖后清空 escalatedFrom |
| 禁止 | 自动降档；触闸后直接判失败 |

实现状态：默认值、命令、投影 {tier, turns, escalatedFrom, reason}、信号①（第 1 轮无产物升档）已实现于 plugins/plan-probe；
信号②③待接入（需要 step 级事件）。注入机制复用 plan-scope 已验证的 systemPrompt.section + 会话投影。

### 3.2 已实现的两条升档信号

| 信号 | 触发 | 实现位置 | 状态 |
|---|---|---|---|
| ① 首轮无产物 | 第 1 轮结束 cwd 无新文件 | session/event + filesNewerThan | 已实现 |
| ② Q1 并发/时序 | 首条用户消息命中 24 条模式之一（并发/限速/令牌桶/退避/重试/QPS/RPS/429/503/concurrency/semaphore…） | projection apply 读 user/message | 已实现 |

实测（真注入，非模拟）：

| 输入 | 结果 |
|---|---|
| 「下载 12 个文件，同时最多 4 个连接，限速 8 rps，超了要退避重试」 | tier=full, escalated-from=q1, reason=限速 |
| 「写一个 CSV 清洗 CLI，输出 UTF-8 BOM」 | tier=light，不升档 |

检测器单测 7/7 通过（4 正例 3 负例）；配置项 escalateOnQ1 可关闭该信号。

## 4. 产物契约

### 4.1 文件

| 文件 | 必填 | 格式约束 |
|---|---|---|
| `CONVENTIONS.md` | light/full | ≤20 行表：`ID | 约定（取值） | 一句理由 | 违规如何被测出` |
| `AMBIGUITIES.md` | light/full | ≤15 条；互斥要求必须标 `【冲突】` + “只能由用户裁决” |
| `P0-EXEC.yml` | light/full | 8–14 条；每条 `id / assert / run / expect`；**full 追加 `source`** |
| `P1-TARGETS.yml` | light/full | 3–6 条；`id / metric / min / max / how`；不作通过判据 |
| `EVIDENCE.md` | full | 四块（事实/约定/歧义/边界）；每条带 `✅可命令` / `👁只能看图` / `🤷不知道` |

`P0` 的硬约束：`run` 必须是**一条可直接执行的命令**；写不出就删条，不许留散文断言。

### 4.2 校验（插件启动时自检）

```
1. 五个文件中该档位要求的都存在
2. P0 条数 ∈ [8,14]，每条含四个必填字段，run 非空
3. full 档：每条 P0 的 source 能在 EVIDENCE 里找到对应编号
4. AMBIGUITIES 中【冲突】项不得被 P0 静默采纳（须有“默认取法”说明）
失败 → 提示补齐后重试，不进入实现阶段
```


## 4.3 验收脚本：资产，不是产物

实测（缩略图任务，n=3）：

| 路线 | 规划 | 实现 | 端到端 |
|---|---|---|---|
| A 清单路线 | 64.4k | 85.2k | 149.6k |
| D agent 产脚本 → 用它实现 | 93.5k | 71.0k | 164.5k（贵 10%） |
| C 人工脚本（无规划） | 0 | 26.0k | 26.0k |

结论：

1. 单次任务用 P0 清单。让 agent 现写脚本并不省，写脚本的成本（fixture/断言/JSON）吃掉了实现侧的收益。
2. 脚本作为项目级资产：同一项目第 3 次做同类验收时，把 P0 固化成 verify/ 下的脚本，之后同类任务直接复用。
3. 复用时实现成本可降到 26k 量级（人工脚本那一臂），这才是脚本路线的正确打开方式。
4. 脚本质量已验证：agent 写的 verify.py 能正确区分「正确实现 / 宽度错误 / 缺 manifest」三种输入。

## 5. 插件接口

```ts
Config = {
  tier: "off" | "light" | "full"        // 默认 off
  scope: "first" | "always"            // 默认 always
  acceptanceFile: string               // 默认 "P0-EXEC.yml"
  sectionOrder: number                 // 默认 42
  gate: { steps: number; tokens: number; seconds: number }
}
```

注入实现（已验证可跑）：

```js
ctx.sessionProjections.register({ key: "planScope", apply: (s, e) =>
  e.type === "turn/start" ? { turns: s.turns + 1 } : s });

ctx.systemPrompt.section({ name: "plan-scope:acceptance", order: 42,
  text: (c) => (scope === "first" && turns(c) > 1) ? "" : readFile(acceptanceFile) });
```

命令：`/plan-tier off|light|full`、`/plan-scope first|always`；投影 `planScope = { tier, scope, turns, phase }`。

## 6. 闸值建议（基于实测）

| 档位 | 步数 | token | 墙钟 |
|---|---|---|---|
| off | 35 | 120k | 700 s |
| light | 30 | 120k | 600 s |
| full | 45 | 180k | 900 s |

**触闸处理**：若实现阶段撞到步数/墙钟闸，允许把档位升一档重跑一次；不允许在触闸后直接判定“任务失败”。

实测触闸率：作用域 first 3/5 撞闸、always 0/5 —— 这是 **scope 默认取 always** 的唯一依据。

## 7. 与 plan-rounds 的关系

| | plan-rounds | plan-probe（本规格） |
|---|---|---|
| 职责 | 多轮自我评审，产出 PLAN-v1..vN + ACCEPTANCE | 一次核查，产出可执行 P0/P1 |
| 注入 | `plan-rounds:contract`（order 41） | `plan-scope:acceptance`（order 42） |
| 关系 | 可共存；rounds=0 时本插件独立工作 | 本插件不依赖 rounds |

合并建议：保留两个 section，order 41 在前、42 在后；两者都从同一份会话投影读配置，避免两套命令。

## 8. 回归验收（改插件必须跑）

七类样例各留一份夹具与验证器，改动后至少跑：

| 样例 | 验证器 | 通过判据 |
|---|---|---|
| CSV 10 万行 | `csv_verify*.mjs` | 行数 100,002 + BOM/CRLF |
| 批量重命名 | `rename_verify.mjs` | 7 项全过 |
| 图片查看器 | `viewer_verify.mjs` + `shift_probe.mjs` | 视口行为 + 位移 200/200 |
| 缩略图 | `thumb_verify.py` | 8/8（≤50KB、480x270、manifest、幂等） |
| 分页 API | `fetch_verify.mjs` | 137 行 + 429 重试 |
| 修既有代码 | `verify_ledger.py` | 5 处缺陷全修 + 格式 |
| 限速下载器 | `dl_verify.mjs` | 12 文件 sha256 + peak≤4 + RPS≤8 |

## 9. 已知限制

- 样例各 n=2~3，除作用域外**没有一条结论有 n≥5 的复现**；比值凡 `t<2` 一律不写进宣传语。
- 验证器本身误判过 7 次（占比高于产物真缺陷）：**判据宁宽勿严，只判规范写明的**。
- full 档在「需求已经写死」的任务上实测更贵（改写任务 1.39×），路由器 Q5 就是为了挡这种情况。
- light 档在探针密集型任务上会**完全无产出**（2/2），这是硬失败，不是成本问题。
- 升档信号③（同一命令 ≥3 次）暂缓实现：该模式更像「卡住」而非「能力不足」，与 Q1 的语义不同，等有实测案例再定。
