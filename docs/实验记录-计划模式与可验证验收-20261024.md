# 实验记录：计划模式与可验证验收（20261024）

## 一句话结论（经受控 A/B 修正后）

真正让实现质量上来的，是**可测的数值目标 + 能自测的工具 + 写死的预算与分层**：四臂受控测试都在 3.86–4.11 分、20 分钟级；
而没有这三者的基线是 3.31 分 / 382k。

**「前置约定文档」本身没有可测增益**：受控 A/B 里，有约定与无约定的拖拽方向都正确（theta −1.20~−1.24 rad），
分数差 0.07（3.94 vs 4.01），小于噪声。早前「约定修方向」的结论是**用像素质心做代理指标造成的误判**，已在文末「结论复核」中更正。

计划文档本身的质量（种子判据召回 95%、矛盾识别 3/3、裁决后修订干净）成立，但它**不能推出实现质量的提升**，两件事必须分开陈述。

## 背景

v1–v3 预设的问题不是「计划不够长」，而是**验收项只测「有没有」，不测「对不对」**：
在 6 份产物里，拖拽方向出现 +4.3 / −46.6 / −27.4 / −30.7 px 的四种结果，而没有任何一份 ACCEPTANCE.md 里有对应断言。

## 四个可复用的结论

### 1. 「补齐约定」比「加一轮复查」有效

重复计划（PR2 两轮 / PR4 四轮）的实质是**同一模型自我复审**：第 2 轮把「自然/干净」改写成可测阈值（数字从 8 个涨到 49 个），
但**设计方案不变**，也审不出它不知道的约定（方向符号、垂直 FOV）。

有效的做法是先产出 CONVENTIONS（21 条，每条带「违规如何被测出」），再写验收。实测同一规划任务：

| 规划器 | 成本 | 验收里带方向断言 |
|---|---|---|
| 极简，无约定 | 52k | 0 条 |
| 极简，喂入冻结约定 | **34.5k** | A05/A06/A07/A32 |

知识前置反而更便宜：模型不需要自己重新推一遍约定。

### 2. 清单必须分层，否则实现者会被拖死

41 条平铺清单（impl1/impl2）：实现者为满足像素级判据，自己 `npm install` + 下载 Chromium + 写打包脚本，603k / 60 分钟仍未收敛。

分层（P0 12 条判定项 / P1 5 条目标区间）+ 35 分钟预算（impl3）：250k / 22 分钟收工，P0 全过，但**质量掉到 1.55**——
因为它只能用 Node DOM/WebGL 桩自测，**从头到尾没有真的看过画面**（其 P0-RESULT 自述：「pixel diff itself not capturable without a browser」）。

### 3. 必须给实现者「看得见」的工具，自述才可信

预装 `shot.mjs`（puppeteer-core + 现有 Chromium，一条命令输出 pinkPct / whitePct / meanLum / rmsContrast + 全部 `window.__*` 数值字段）之后：

- impl4：P0 全过，且**主动写下自己没过的项**（rmsContrast 34.9 → FAIL）
- 我用 `orbit_probe.mjs` 独立复核：theta −1.00 / +2.00、radius ±2.54，与其自述完全一致

这是本系列第一次「模型自述经得起独立复核」，前提是**诊断对象可读**（P0-12 的硬要求）。

### 4. 观感项给出具体配方才动得了

contrast 是六臂里谁都没解决的一项（最高分的 C-std2 也只有 4 分）。impl5 给了 6 条按效果排序的手段：
地面明度梯度、天空梯度跨度 ≥80、树干压暗、投影加深、四角暗角 ×0.82、缩短雾距。

结果：rmsContrast **30.0 → 49.6**，cost 反而最低（173.6k）。
结论：**抽象的「要好看」不会被执行，具体的「把地面近景压到 120,132,96」会**。

## 消融：只给工具、不给约定（樱花任务）

| 臂 | 约定 | 工具 | 成本 | 分数 | 方向可验证 | contrast |
|---|---|---|---|---|---|---|
| C-min2 | ✗ | ✗ | 382k | 3.31 | ✗ | 2 |
| 只给工具 | ✗ | ✓ | 218k（25 分钟超时被杀） | **4.38** | ✗（无诊断接口） | 2 |
| impl5 | ✓ | ✓ | 173.6k | 4.00 | ✓ theta −1.00 | 4 |

这条消融把两者的贡献分开了：

- **工具**能让画面指标被自我优化（只给工具的臂把粉色占比调到 9.85%，接近评分器最优点 10%，自建了 angles/wire/bench 等 10 余个自测脚本）
- **约定**才让「方向」变成可判定、可复核的东西；只给工具时它连诊断字段都没暴露，方向无法验证
- 只给工具那臂**分数最高（4.38）却方向不可验证、对比度仍是 2** —— 说明 score3 这个分数不度量正确性，用分数选方案会选错

## 指标口径问题（重要）

`score3.py` 的 `struct` 不是「与参考图的相似度」，而是**相邻视角帧之间的 IoU**：

```
ious = [iou(views[i], views[i+1]) for i in range(3)]
struct = 5 if (1 - iou) >= 0.5
```

即「换视角时画面变化越大分越高」。impl5 的 iou 0.531（视角间偏像）→ struct 4；C-std2 的 0.402 → struct 5。
**4.44 与 4.00 的差距里，有 0.4 分来自视角差异而不是画面质量。** 若要用它评「好不好看」，此口径需要重定义。

另外 `density` 的最优点硬编码在粉色占比 10%（`5 - |pink-10|/3`），与任务文案里的「落花稀疏轻盈」直接冲突：
执行「稀疏」的实现会被系统性扣分。这个冲突在 batch32 就已出现（C-min2 粉色 1.86% → 3.31 分）。

## 计划可靠性：种子判据召回 + 重复一致性

前几节验证的是「实现」，这一节验证的是**计划本身可不可信**。做法：准备三份短需求，每份埋 7–8 个
必须提前锁定的沉默契约（需求文本不提、但猜错就错），标准答案单独保存（`KEYS.md`，不给被测模型）。

### 召回（单次运行）

| 任务 | 埋的判据 | 命中 | 成本 | 备注 |
|---|---|---|---|---|
| CSV 导出 | 7 | **6** | 56.2k / 28 步 | 漏：表头重复列名 |
| 批量重命名 CLI | 8 | **8** | 65.7k / 22 步 | — |
| 颜色混合器 | 7 | **7** | 80.2k / 23 步 | — |
| 合计 | 22 | **21（95%）** | 202k | — |

命中不是「提醒一句」，而是给出可判定的取值 + 违规检测，例如：

- 排序：「自然序；违反检测：`LANG=C` 与 `LANG=zh_CN.UTF-8` 各跑一次，两行编号映射 diff 必须为空」
- 冲突：「`rename` 静默覆盖（F8 实测），`link` 的 EEXIST 是原子的 → 先用原子占位再改名」
- 取整：「`round(pct*255/100)` 半值向上，50/50 必须是 `#800080` 而非 `#7f007f`」
- 键盘：「`ArrowUp=+1`、`PageUp=+10`、`Home=0`、`Shift+Arrow=+1`（无加速），逐键实测」

### 重复一致性（同需求跑两次）

| 任务 | 约定条数 | 成本 | 决策取值是否一致 |
|---|---|---|---|
| 重命名 r1 / r2 | 20 / 23 | 65.7k / 55.7k | ✓ 自然序、补零宽度 max(4,…)、原子占位、不递归，两次一致 |
| 混合器 r1 / r2 | 26 / 16 | 80.2k / 107.3k | ✓ sRGB 相加、半值向上（#800080）、ArrowRight=+1、PageUp=+10，两次一致 |

**结论：决策层稳定，形式层不稳定。**

- 稳定：同一个问题两次给出同一个答案（这是可靠性真正要的）
- 不稳定：条数 ±20%（16↔26）、语言会切换（同一任务一次英文一次中文）、成本 ±30%（80k↔107k）

形式不稳定会带来两个实际问题：人工复核要同时读中英两版；跨任务的成本预算不好估。

### 矛盾需求：是否指出冲突，而不是静默择一

最后一块可靠性：真实需求常常自相矛盾。构造一份含 3 条硬冲突 + 1 条弱冲突 + 3 条易误判为冲突的需求
（单文件数据看板：极简 vs 8 组对比、8 色区分 vs 只用黑白灰、200 ms 可交互 vs 20 MB 内联图）。

| 判据 | 期望 | 实际 |
|---|---|---|
| X1 极简 vs 8 分组 | 指出互斥 | ✓ A1【致命】，给了两种读法、代价、判别探针、默认值 |
| X2 8 色 vs 黑白灰 | 指出互斥 | ✓ A2【致命】，附 8 级灰阶实测（相邻 ΔL*≥8、最浅一级仅 1.196:1） |
| X3 200 ms vs 20 MB | 指出互斥 | ✓ A3【致命】，附实测：首个输入 302.7 ms、图解码 357.0 ms |
| N1 单文件 vs 不联网 | **不得**误报 | ✓ 未列为歧义 |
| N2 8 分组 vs 单文件 | **不得**误报 | ✓ 未列为歧义 |

处理形态（A1 原文节选）：

> **我取**：乙。8 条线画在同一个绘图区里，不要图例……这是对 R1 的**已知偏离**，必须写进 PLAN 的风险项。
> **错了会坏什么**：……这不是技术问题，是需求自相矛盾，**只能由用户裁决**。
> **最便宜的判别探针**：把本文 A1 段落原样发给用户，问一句「页面允许出现 8 条线 + 3 个小按钮吗？」
> 默认（用户不回）：取乙，并在页面里完全不出现图例/标题/坐标轴文字。

PLAN 开头也据此写下：「三条需求互斥，**先裁决再动手**；不裁决就按默认列执行，并把偏离写进交付说明。」

成本 46.6k / 22 步；除 3 条硬冲突外，另列 A4–A11 八条真实歧义（数据源缺失、MiB vs base64、背景是否也受单色约束、
「可交互」从哪一刻算、大数字是什么、窗口语义、「别的元素」的边界、「高清」的分辨率）。

### 多轮修订：用户裁决后，冻结的计划能不能干净地改

用 `dsh --session-id` 续接同一会话，第二轮只说「A1 取甲：只保留一个数字+一条线，8 组与配色取消；仍只用黑白灰」。

| 检查项 | 结果 |
|---|---|
| 是否产出变更清单 | ✓ `REVISION.md`（5.9 KB）：删除 / 改写 / 保持不变三段 |
| 删除是否逐条可追溯 | ✓ 约定 5 条（灰阶梯级、两条阈值、虚线通道、`aria-pressed`、Tab 序）+ 验收 7 条（AC-06…AC-11、AC-26），每条附理由 |
| 陈旧条目是否残留 | ✓ 全文仅剩「已删除 / 已关闭 → 甲 / ~~划除~~」三处书签式提及，无失效要求 |
| 歧义是否结案 | ✓ A1 → 【已裁决 → 甲】，A2 作废，A3 仍标为唯一阻塞项 |
| 是否衍生新问题 | ✓ 新开 A1′：只剩 2 个元素时，7/30/90 范围切换怎么存在 |
| 跨文件一致性 | ✓ 需求 2 作废后自动推出：大数字从「8 组合计」变为「当前值」→ C16 不再需要「合计可能超 100%」分支；P4 从「灰阶梯级 + 8 种虚线」缩为 1 个颜色；P6 从「3 按钮 + 键盘」改为「零控件 + 循环」 |

成本 **34.8k / 5 步**（续接会话，不需要重读整个仓库）。

这是可靠性里最难的一项：不是「能不能生成」，而是**改的时候会不会留下自相矛盾的残骸**。实测没有。

## 结论复核：受控 A/B 推翻了「约定修方向」的因果判断

前面的结论建立在一个前提上：**无约定的基线会把拖拽方向写反**。这个前提来自像素质心探针
（V3 +4.3、PR2 −46.6、C-min2 −27.4、C-std2 −30.7 px）。后续发现该探针不可靠：impl2 用同一探针测出 −12.4 px，
而读状态是 **−1.000 rad（正确）**。因此做了一个受控 A/B 重新判定。

### 设计

两臂完全相同：同一任务、同一 profile、同样预装 `shot.mjs`、同样要求暴露 `window.__SAKURA__`、同样给 P1 数值目标
（粉 8–12% / con ≥ 45 / 白 ≤ 0.5% / 树高 55–85%）、同样 20 分钟预算。
**唯一差异**：B 臂多一段 5 行「方向约定」（theta 增减符号、半径增减、phi 夹紧、垂直 FOV）。每臂跑 2 次。

### 结果

| 臂 | 次 | 拖右 200 px 的 theta 变化 | 拖左 | 分数 | contrast | 粉色% |
|---|---|---|---|---|---|---|
| A 无约定 | r1 | **−1.24 rad** | +2.48 | 3.86 | 4 | 5.95 |
| A 无约定 | r2 | **−1.20 rad** | +2.40 | 4.02 | 4 | 7.14 |
| B 有约定 | r1 | **−1.24 rad** | +2.48 | 4.11 | 4 | 12.20 |
| B 有约定 | r2 | **−1.20 rad** | +2.40 | 3.90 | 4 | 6.23 |

**四臂方向全部正确，且符号幅度一致（−1.2 / +2.4）。** 分数 A 均值 3.94、B 均值 4.01，差 0.07，远小于噪声。

### 修正后的结论

1. 早前「无约定基线的方向会写反」**不成立**——那是像素质心探针的误判，不是实现错误。改口径后无法再用它证明约定的因果作用。
2. 在这份受控测试里，**约定文档没有可测增益**（0.07 分，且 B 臂 r2 反而更低）。
3. 真正带来提升的是三件事，它们在两臂里都有：**可测的数值目标**（con ≥ 45 这类）、**能自测的工具**、**写死的预算与分层**——
   对比 C-min2（无工具、无数值目标、382k）：3.31 分；这四臂（都有三者）：3.86–4.11 分，且都在 20 分钟级。
4. 计划质量实验（下文召回 95%、矛盾识别 3/3、裁决后修订干净）**仍然成立**，但它衡量的是「计划文档本身的可靠性」，
   **不能推出「实现质量因此提升」**。两件事必须分开陈述。

### 方法教训（本实验最大的收获）

- **不要用代理指标做因果推断**：像素质心会随场景内容漂移，把正确实现测成反向。方向、状态类判据必须读状态。
- **没有对照组的「前后对比」会归因到最近一次改动**：impl2→impl3→impl4→impl5 每次都改了 2–3 个变量，
  所以「impl5 更好」不能证明是打光配方或约定的功劳。受控 A/B 才是判据。
- **n=1 的差异不可信**：本实验里同臂两次运行差 0.16–0.21 分，接近不同臂之间的差距。

## 优化原型：窄产物（v2）+ harness 硬闸

依据「主会话读 PLAN 3 次 / 读 ACCEPTANCE 34 次」与「41 条断言平均 0.95 条命令/条」，做了两个改动（未提交）：

1. `candidates/flash-plan-probe-v2.patch.yml`：产物收窄为 `CONVENTIONS.md`（≤20 行 + 事实附录）、`AMBIGUITIES.md`（≤15 条，冲突标【冲突】）、
   `P0-EXEC.yml`（每条必须带可执行 `run`）、`P1-TARGETS.yml`（只给数值区间）；去掉 PLAN/EDGES 正文。
2. `exp/run_plan_gated.py`：步数 / token 超限由 harness 直接 `killpg`，不再依赖提示词自觉。

| 断言可执行性 | 无法机判为主 | **14/14 条带 `run`，`bash -n` 全过** |

### 硬闸验证

- 冒烟：`max_steps=3` 的计时器任务在 4 步被掐，`summary.json` 记录 `killed: steps 4 > 3`。
- 真实任务：v2 跑 CSV 在 23 步 / 52.3k 内自然收尾，未触发。

### 已知缺口

- P0 部分 `run` 引用实现者需自行创建的辅助脚本（如 `checks/export-run.mjs`）——「可执行」目前是**语法可执行**，
  端到端可执行需要实现简报同步要求这些脚本，尚未验证。
- 硬闸按 `step_end` 事件计数，若模型在单步内做很久，闸门不会提前介入（只有时间闸兜底）。

### 实现级 A/B：宽产物清单 vs 窄可执行协议（CSV 任务）

两臂同一任务、同一 profile、同一硬闸（70 步 / 350k / 1500 s），唯一差异是**给实现者的验收材料**：

- A：v1 的 `ACCEPTANCE.md`（散文断言为主）
- B：v2 的 `P0-EXEC.yml` + `P1-TARGETS.yml`（每条带可执行 `run`），并要求「交付前逐条跑通」

| | A（v1 宽产物） | B（v2 窄协议） |
|---|---|---|
| 步数 | 51 | **21** |
| 新 token | 114.9k | **55.2k** |
| 墙钟 | 718 s | **222 s** |
| 10 万行导出（独立验证） | ✓ 100,001 行 / 5.9 MB | ✓ 100,002 行 / 3.96 MB / 1.67 s |
| BOM / CRLF | ✓ / ✓ | ✓ / ✓ |
| 边界单元格（逗号/引号/空值） | 内建 6 行边界样本 | 表格内含 `a,b`、`say "hi"`、空值 |
| 自检方式 | `ACCEPTANCE-RESULT.md` 47 条 PASS + `tools/verify.mjs` + Excel 复核脚本 | `p0run.mjs` + `run-p0.sh`，14/14 ALL_PASS |

**同等实质合规，B 便宜一半。** n=1，只能说“与假设一致”，不能说已证明。

### 一个意外收获：协议同时固定了「fixture 契约」

我最初的独立验证器把 B 判为失败（只导出 22 行）——因为默认视图只有 20 行；实际它用 `?rows=100000` 控制规模，
而这个参数**写在 P0-EXEC 的 `run` 里**。补上参数后 100,002 行、3.96 MB、1.67 s，全部达标。

A 的散文清单没有规定如何触发大数据量，验证器只能靠猜。也就是说：**可执行断言顺带把「怎么测」也固定下来**，
这是窄协议一个未被预期的好处。

反向的教训同样成立：**独立验证器必须采用协议声明的 fixture**，否则会把自己的盲区记成对方的缺陷。

## 适用边界（决策规则）

这套流程不是默认选项。按下面三条判断要不要上：

| 条件 | 判断 | 依据 |
|---|---|---|
| 任务涉及**模型没有可靠先验的约定**（3D 轨道符号、垂直 FOV、坐标系手性） | **必须**上：先产出 CONVENTIONS 再写验收 | 樱花：基线方向错、不可验证；有约定后可验证且正确 |
| 评分里有**模型看不见的维度**（对比度、泛白、构图占比） | 上**工具**，并把它变成可读数字 | 盲测臂 contrast 2/5；给工具后 4/5 |
| 任务属于模型熟悉的领域（2D 平移缩放、计时器状态机、表单校验） | **不要上**：纯开销 | 两个任务族基线全过，零约定 |

还有一条独立于任务类型的规则：**验收清单必须分层**（P0 判定项 / P1 目标区间），
平铺 41 条会让实现者把预算耗在配角断言上（603k / 60 分钟未收敛）。

## 适用边界之外的一条警告

**不要用聚合分数来决定采用哪个方案。** 只给工具那臂分数最高（4.38），但方向不可验证、对比度 2/5；
评分器不度量正确性，只度量「粉量 / 视角差异 / 对比度」。正确性必须由独立的、能读状态或行为的验证器判定。

## 复现方式

1. 规划：`dsh --profile headless --patch candidates/flash-plan-probe-v1.patch.yml "<任务>"`（产出 FACTS / CONVENTIONS / AMBIGUITIES / EDGES / PLAN / ACCEPTANCE）
2. 把 CONVENTIONS.md 与 `templates/P0-P1-验收清单-模板.md` 合并成实现简报
3. 把 `tools/shotkit/` 拷进工作目录（已含 node_modules 时只需 shot.mjs），允许实现者自测
4. 复核：`orbit_probe.mjs` 读 `window.__*` 诊断字段，不要用像素质心代理方向（实测会把正确的 −1.000 rad 误判成 −12.4 px）

## 未解决

- `struct` 口径（相邻视角 IoU，非与参考图相似度）与 `density` 目标（硬编码 10%）都需要重定义
- 前置约定一次性 173–255k，尚未实测「跨任务复用」的摊销收益
- 所有臂均为 n=1，方差未估计；pilot 阶段 bootstrap CI 提示差异 < ~0.5 分不应下结论
- 「为什么 3D 符号会错、2D 不会」只有推断，没有直接测量：可让模型在无 three.js 的情况下手写三维旋转，检验是否是「三维旋转约定」的通病
- 只给工具那臂（4.38 分）超时被杀，未验证它在不受时间限制时是否也会暴露诊断接口

| 合规 | 4/4 | 4/4 |

作用域没有产生可测差异：8 次全过，v2 的 12.5k 差异落在同臂方差（16–19k）内。
原因是系统提示词本来就每轮重发，「仅首轮」只是叫模型别回头核对，它并不真的每轮重跑 P0。

### 真正的实现路径（下一步）

`ctx.systemPrompt.section(section)` 返回注销函数，所以「仅首轮」应写成：

```js
const dispose = ctx.systemPrompt.section({ id: "plan:acceptance", content });
ctx.on("turn:end", ({ turn }) => { if (turn === 1) dispose(); });
```

这样第 2 轮起提示词里真的没有这段，token 与行为差异才可测。本轮是提示词级模拟，
只能说明「叫模型别核对」没有收益，不能替代插件级 A/B。

### 阶段结论

- 全量版 v3 在「问题清楚」的任务上多付 21%（108.5k vs 89.5k）且零合规收益 → 默认用 v2，v3 只在需求含未知项时启用。
- 作用域开关在当前形态下无差异；要拿到真实差异必须走插件注入 + 首轮后注销。

## 第七阶段：插件级作用域（真注入，不是提示词模拟）

### 实现

`plugins/plan-scope`：用 `ctx.systemPrompt.section()` 注册验收清单，靠会话投影数 `turn/start`；
`scope=first` 时第 2 轮起 `text()` 返回空串 → 提示词里真的没有这段。

```js
ctx.sessionProjections.register({ key: "planScope", apply: (s, e) => e.type === "turn/start" ? { turns: s.turns + 1 } : s, ... });
ctx.systemPrompt.section({ name: "plan-scope:acceptance", order: 42,
  text: (c) => scope === "first" && turns(c) > 1 ? "" : readFile(acceptanceFile) });
```

加载方式：profile 层 `- insert: [{ id: plan-scope, name: "file:///.../lib/index.js", config }]`；
插件目录内软链 `@deepseek-ai/cordis`、`zod` 到 DSH 安装目录。冒烟标记 `/tmp/plan-scope-loaded.txt` 确认 apply 真的执行。

### 结果（同产物 v3 P0-EXEC，n=2）

| 作用域 | 步 | 新 token | 墙钟 | 触闸 | 独立检查 |
|---|---|---|---|---|---|
| 每轮（always） | 38 / 44 | 98k / 90k | 508 / 504 s | 0/2 | 8/8、8/8 |
| 仅首轮（first） | 46 / 31 | 119k / 81k | 677 / **903 s（超时）** | **2/2** | 8/8、8/8 |

| 汇总 | always | first |
|---|---|---|
| token 均值 | 94.0k | 100.0k |
| 触闸次数 | 0/2 | **2/2（1 次超步数、1 次超时）** |
| 合规 | 2/2 | 2/2 |

### 结论

- 真注入下，「仅首轮」并没有省 token（100.0k vs 94.0k，反而略高），但**稳定性明显更差**：两次跑都撞到闸（46 步 > 45、903 s > 900 s）。
- 解释：清单消失后模型失去了「还剩哪些没做」的锚，倾向于反复自我检查与试探，步数与时间被拉长；token 因为上下文变短被抵掉一部分，最终抵消。
- 实操建议：**默认用「每轮都生效」**；「仅首轮」只在明确知道任务短、且要压上下文长度时使用。
- 样本仍小（n=2），但两次都触闸不是随机噪声能轻易解释的，值得后续 n=5 复核。

### 插件级实验顺带修掉的问题

| 问题 | 修法 |
|---|---|
| 插件 `import "@deepseek-ai/cordis"` 解析失败 | 插件目录内软链 cordis / zod 到 dsh 安装目录 |
| 只传 `C-min2-wb.yml` 时插件根本没加载 | 新建 `C-min2-wb-scope.yml` = 基础层 + insert 层 |
| 无法确认 apply 是否执行 | 插件内写 `/tmp/plan-scope-loaded.txt` 标记 |
| bash 里 `node -e`/heredoc 反复被转义打断 | 把改写脚本落成 `.mjs` 文件再执行 |

### 第七阶段补充：n=5 复核

| 作用域 | 各次 token（k） | 均值 | sd | 步数均值 | 撞闸 |
|---|---|---|---|---|---|
| 每轮 always | 98 / 90 / 105 / 74 / 85 | 90.4k | 11.9k | 36.4 | **0/5** |
| 仅首轮 first | 119 / 81 / 98 / 117 / 91 | 101.2k | 16.5k | 41.0 | **3/5**（2 次超步数、1 次超时） |

配对差（first − always）：+21 / −9 / −7 / +43 / +6，均值 +10.8k，sd 21.6k，t≈1.12，**不显著**。
token 比值 1.12，落在噪声内。

**唯一的稳定差异是撞闸率：0/5 vs 3/5。** 合规两边都是 5/5（独立检查 8/8 全过）。

因此修正第七阶段 n=2 时的说法：「仅首轮更费 token」不成立（不显著）；
成立的是「仅首轮更容易失控撞闸」——清单消失后模型倾向于多做自我检查，步数与墙钟被拉长，偶发触顶。

实操：**默认「每轮都生效」**；「仅首轮」只在明确短任务、且需要压上下文时用，并且要给更宽的步数闸。

## 第八阶段：第六个样例——修既有代码（5 处埋点缺陷）

任务：给定一个能跑但算错的 `ledger.mjs`（4 处计算缺陷 + 1 处格式缺陷：`toFixed` 非四舍五入、空金额静默丢弃、TOP3 只要 2 个、并列不排序、输出不补两位小数），
要求「修好、接口不变、别重写」。验证器 `verify_ledger.py` 独立用 Decimal 复算真值并比对整份输出 + stderr 告警 + 退出码。

### 规划阶段：两档产物都能全找出缺陷

|---|---|---|---|---|
| v2 轻量 | 22 | 63k | 276 s | **5/5** |
| v3 全量 | 18 | 90k | 354 s | **5/5** |

两档都点名了四舍五入、空金额告警、TOP3 数量、并列排序、两位小数——**在「代码就在眼前」的任务上，全量版没有额外发现。**

### 实现阶段

| 臂 | 步 | 新 token | 独立检查 |
|---|---|---|---|
| v2 产物 | 14 / 18 | 42k / 50k | 5/5 全过 |
| v3 产物 | 23 / 18 | 70k / 58k | 5/5 全过 |

|---|---|---|---|
| token 均值 | 46.0k | 64.0k | **1.39** |
| 合规 | 2/2 | 2/2 | 无差异 |

### 结论

- 缺陷全被找出来，两边都是 5/5：**当错误已经写在代码里、且有可执行判据时，规划档位的差别不体现在「找不找得到」。**
- v3 产物让实现阶段贵了 39%（64k vs 46k），因为要读更多约定文本，而任务本身只需改 20 行。
- 这类「给定代码 + 明确规范」的任务，**用 v2 就够**；v3 的价值仍在「需求含未知、要先探索」的场景。

## 第九阶段：第七个样例——限速下载器（并发 / 限流 / 重试）

夹具：本地服务端 12 个文件，**并发 >4 或每秒 >8 个请求即返回 503**；验证器读服务端统计（peak 并发、peak RPS）+ 逐文件 sha256 + 临时文件残留 + stderr 的 `DONE 12 <重试数>`。

### 规划阶段：轻量版第一次彻底失败

| 版本 | 结果 | 步 | 新 token | 撞闸 |
|---|---|---|---|---|
| v2 轻量 | **两次都没产出任何文件** | 8 / 31 | 76k / 101k | token 闸、步数闸 |
| v3 全量 | 产出 EVIDENCE / CONVENTIONS / P0 / P1 | 19 | 88k | 无 |

两次失败的形态一致：规划 agent 一直在起服务端、压并发、看 503 行为，**没有「必须先落盘」的里程碑**，被闸掐断时磁盘上什么都没有。
v3 的阶段 1 要求先写 EVIDENCE，等于强制它把探索结果落盘，反而收敛得更快。

### 实现阶段（只有 v3 产物可用，n=2）

| 次 | 步 | 新 token | 独立检查 | peak 并发 | peak RPS |
|---|---|---|---|---|---|
| 1 | 7 | 46k | 6/6 全过 | 2 | 7 |
| 2 | 6 | 48k | 6/6 全过 | 2 | 7 |

12 个文件 sha256 全部匹配、无 `.part` 残留、`DONE 12 0` 正确输出。**这是全部样例里最便宜的一次实现（46–48k）。**
原因：计划把并发上限、限流上限、完成行格式、重试语义都钉死了，实现阶段几乎没有试探。

### 结论

- 需求含**并发/时序/限流**这类「不跑起来就看不见」的约束时，**轻量版会退化成无产出的空转**；全量版的「先写 EVIDENCE」是必要的锚。
- 这是本课题里第一个「全量版唯一可用」的样例，也是对 v3 存在价值最直接的一次证据。
- 实现阶段反而最省：**计划把隐式约束钉死，实现付的钱最少**。

### 验证器第 7 次误判

`execFileSync` 成功时只返回 stdout，我据此判定「缺 DONE 行」，两个实现都被判失败；手动跑发现 `DONE 12 0` 确实在 stderr。
改用 `spawnSync` 同时取 stdout/stderr 后，两份都是 6/6 全过。

## 第十一阶段：换一个方向——把验收变成可执行脚本

问题：既然清单里的 `run` 本来就是命令，**为什么不直接给一份可执行的验收脚本，连散文一起省掉？**

三臂对照（缩略图任务，n=3）：

| 臂 | 交付给实现者的东西 | token 均值 | sd | 独立检查 |
|---|---|---|---|---|
| A | P0 清单（散文 + 命令，现状） | 85.2k | 24.5k | 3/3 全过 |
| B | P0 清单 **+** 验收脚本 | 100.7k | 20.3k | 3/3 全过 |
| C | **只有验收脚本** | **26.0k** | 8.4k | 3/3 全过 |

| 对比 | 比 | t | 结论 |
|---|---|---|---|
| C / A | **0.30** | −3.96 | 显著，脚本臂便宜 70% |
| B / A | 1.18 | 0.84 | 加了脚本反而更贵（上下文变长） |

### 这是本轮最大的调整空间

1. **可执行脚本单独用，效果最好**：同样 3/3 全过，成本只有清单的 30%，方差也更小（sd 8.4k vs 24.5k）。
2. **清单 + 脚本是最差组合**：两份重叠的判据都要读，成本反而最高。
3. 含义：**规划产物的价值 ≈ 其中「可执行」的那部分**；把散文压成脚本，比把散文写得更短更有效。

### 但要诚实标注这个实验的边界

- 验收脚本是**我手写的**，其作者成本没有计入；它不是「规划 agent 自己产出的」。
- 因此严格说，这一轮证明的是「**给现成脚本比给清单便宜**」，还没有证明「agent 能同样便宜地产出脚本」。
- 这正好是下一步要测的：让规划 agent 直接产 `verify.py`（而不是 P0 清单），再看
  (a) 脚本质量（能否通过自己的夹具）(b) 实现阶段成本 (c) 端到端总成本（规划 + 实现）。

### 对规格的影响（候选改动，待验证后再改）

| 现状 | 候选 |
|---|---|
| light 档产出 P0-EXEC.yml（8–14 条命令） | light 档产出 `verify.py`（单个可执行检查器） |
| P0 每条 `run/expect` | 脚本内一组断言 + 退出码语义 |
| 冲突由 AMBIGUITIES 标【冲突】 | 脚本里无法判定的项必须显式 `SKIP(reason)` 并计入报告 |

## 第十二阶段：让 agent 自己产出验收脚本（端到端总账）

问题：既然「给现成脚本」比「给清单」便宜 70%，那让规划 agent 直接产脚本，端到端是否更划算？

| 路线 | 规划 | 实现（n=3 均值） | 端到端 | 独立检查 |
|---|---|---|---|---|
| A 清单路线（基线） | 64.4k | 85.2k | **149.6k** | 3/3 |
| D agent 产脚本 → 实现用它 | 93.5k（26 步） | 71.0k（87/80/46） | **164.5k** | 3/3 |
| C 人工脚本（无规划） | 0 | 26.0k | **26.0k** | 3/3 |

### 脚本质量：合格

agent 产出的 `verify.py` 在三个对照上表现正确：

| 输入 | 结果 |
|---|---|
| 正确实现 | `pass: true` |
| 变异体 1（宽度 480→400） | `pass: false` |
| 变异体 2（不写 manifest） | `pass: false` |

它还会自造 fixture、标注 `skipped`、给出每条 check 的 detail。质量不是问题。

### 结论：脚本路线不是普适优化，而是「资产路线」

- 一次性任务上：93.5k（写脚本）+ 71.0k（实现）= 164.5k，**比清单路线贵 10%**。
  写脚本比写清单贵（要处理 fixture、断言、JSON 输出），省下的实现成本抵不掉。
- 只有当脚本**可复用**（同一项目反复跑、或跨任务族共用）时，26.0k 那条线才可达。
  人工脚本那一臂的 26.0k 就是「复用后的上限」。
- 因此正确的形态不是「每任务产脚本」，而是**建立可复用的验收库 + 每任务只补少量条目**。

### 对规格的修正（第二版候选）

| 项 | 第一版 | 修正后 |
|---|---|---|
| light 产物 | P0-EXEC.yml | 仍为 P0-EXEC.yml（一次性任务的最优解） |
| 脚本 | 无 | **可选资产**：项目级 `verify/` 目录，跨任务复用 |
| 触发脚本化 | — | 同一项目第 3 次以上做同类验收时，把 P0 固化成脚本 |

一句话：**脚本是资产不是产物。** 单次任务用清单，长期项目把清单沉淀成脚本。

## 第十三阶段：lean-v3 的预算约束是否诱发「省掉自测」

假设（用户提出）：标准说不清时，lean-v3 的预算条款会让 agent 跳过中间自测，从而抬高错误率；对策是放宽预算 / 要求连续两轮自测通过 / 直接删掉预算只留工程纪律。

做法：以 `presets/flash-lean-ptc-v3.patch.yml` 为基线做四个变体（只改三处措辞）：

| 臂 | 改动 |
|---|---|
| A | 原样（<=20 turns，验收门通过即交付） |
| B | 轮数预算 20→40，删掉「under the step budget」的催促 |
| C | 「验收门通过即交付」→「必须连续两轮通过才交付」 |
| D | 删除预算条款 + 每改必测 + 连续两轮通过 |

两个任务：① ledger 修错（标准以代码意图为准）② 网页缩略图（业务口径：快/不糊/不变形）。

### 结果一：没有观察到「省自测导致错误」

| 任务 | A | C | D | 通过率 |
|---|---|---|---|---|
| ledger 修错 | 66.7k（30/61/109） | 59.7k（46/49/84） | 54k（n=1） | 全部 3/3 |
| 缩略图（口径模糊） | **77.3k**（44/89/99） | 109.7k（83/120/126） | 100.5k（86/115） | 全部 3/3 |

- 放宽预算或强加两轮自测，**token 反而涨 30%~42%**，正确率不变（都 100%）。
- D 臂（无预算）在 ledger 上撞到 46 步的硬闸 —— 这正是 lean-v3 当初要防的 TLE 失败模式。
- 结论：这条假设在本批任务上不成立。错误率没有随预算收紧而上升。

### 结果二：真正的不确定性在「判据」，不在「自测轮数」

缩略图任务第一轮我自己的验证器把八次运行全判成失败（`失败:width`）。查明是**验证器的错**：我用「宽度 320–800」判，而竖图的宽度天然是 270（长边才是 480）。改成「长边 320–800」后 8/8 通过。

这是本项目第 8 个验证器缺陷，且是最典型的一个：**标准说不清时，判据本身才是最大的误差源。** agent 没有省自测，是我的尺子量错了。

### 建议（对 lean-v3 的修正，不动预算）

保留全部预算条款，只加一条：

> 标准不明时，先用一条命令把关键阈值钉死（尺寸/字节数/时间），并在交付说明里写出选了哪个值、为什么。
