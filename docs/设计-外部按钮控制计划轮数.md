# 设计：用外部按钮控制「重新计划轮数」

目标：v3 预设不动；用**预设 + 外部按钮**决定开工前重复计划几次（默认关闭 / 2 次 / 增强 4 次）；计划过程在后台跑，前台只显示等待与状态图标。

## 1. 可行性依据（已核对 DSH 0.2.1-rc.2 的实现）

| 需要的能力 | DSH 现成机制 | 出处 |
|---|---|---|
| 按钮受控的开关 | 斜杠命令 `ctx.commands.register(...)` | `dsh-plan-mode/lib/index.js` |
| 前台实时看到后台状态 | **会话投影** `ctx.sessionProjections.register(...)` + 客户端 `useProjection(...)` | `dsh-plan-mode` / `dsh-client-ui-plan` |
| 客户端触发 | `session controller` 的 `prompt`（提交一条消息） | `dsh-api-session-controller/lib/client.js` |
| 把计划注入执行阶段 | `ctx.systemPrompt.section(...)` | `dsh-plan-mode` |
| GUI 里已有 plan mode | web profile 第 279–291 行 `planMode: true` | `~/.dsh/profiles/web/cordis.patch.yml` |

结论：**不需要改 DSH 内核**，两个插件（host + client）即可，全部走官方扩展点。

## 2. 组件与数据流

```
[按钮 关闭/2/4]  --prompt("/plan-rounds 2")-->  [host 命令处理]
                                                      |
                                          写入本会话状态 rounds=2
                                                      |
        [host 规划循环]  round 1..N  --更新-->  [sessionProjection: planRounds]
                                                      |
                                    [客户端 useProjection] --> 状态图标/进度
                                                      |
                                   规划结束 --> 注入 systemPrompt.section --> 主循环执行
```

关键点：**前台不参与计算**。规划循环在 host 侧、turn 的 pre-step 阶段跑；前台只是订阅投影，天然就是"等待 + 图标"。

## 3. 投影 schema

```ts
type PlanRoundsProjection = {
  rounds: 0 | 2 | 4        // 目标轮数，0 = 关闭
  phase: 'idle' | 'planning' | 'ready' | 'executing' | 'failed' | 'cancelled'
  round: number            // 当前第几轮（1-based）
  total: number
  planFile?: string        // 最终计划落盘路径（PLAN-vN.md）
  acceptanceItems?: number // 验收条目数
  updatedAt: number
}
```

## 4. 规划循环（后台）

每一轮都必须是**累积批评**，不是重新生成：

| 轮 | 输入 | 输出 |
|---|---|---|
| 1 | 用户需求 | `PLAN-v1.md`：任务拆解 + 初版验收项 |
| 2 | 需求 + v1 | `PLAN-v2.md`：以"严格评审者"身份否掉 v1 的薄弱项；每条需求转成**可执行判定命令** |
| 3 | 需求 + v2 | `PLAN-v3.md`：补充边界条件、最坏规模、失败路径 |
| 4 | 需求 + v3 | `PLAN-v4.md`：冻结版，附验收命令清单（`ACCEPTANCE.md`） |

硬约束：

- 每轮上限 **90 s**，总预算 **300 s**；超时用当前最好版本继续
- 单轮失败不中断，降级并把 `phase` 标 `failed`，主循环照常执行
- 用户在规划中发新消息 → 取消循环，标 `cancelled`，按新需求重来
- 轮数变更只对**下一个 turn** 生效，避免中途改契约

## 5. 前台表现

| 状态 | 图标 | 文案 |
|---|---|---|
| 关闭 | 空心圆 | 计划：关 |
| 计划中 | 旋转圈 + `2/4` | 正在细化验收标准… |
| 完成 | 实心勾 | 已生成 4 版计划（12 条验收项） |
| 执行中 | 箭头 | 按第 4 版计划执行 |
| 失败降级 | 感叹号 | 计划生成失败，已退回直接执行 |

按钮本身三态：`关闭 / 2 次 / 4 次（增强）`，点击后立即回显（乐观更新），投影回来再对齐。

## 6. 预设侧（v3 不动）

新增 additive profile patch：`presets/plan-rounds.patch.yml`

```yaml
- id: plan-rounds
  name: "@local/dsh-plan-rounds"
  config:
    rounds: 0          # 默认关闭
    perRoundMs: 90000
    totalMs: 300000
    persistPlans: true  # 写 PLAN-v*.md 便于事后审计

```

v3 的 `flash-lean-ptc-v3.patch.yml` 完全不动；两者叠加使用。

## 7. 成本估计

每轮一次 LLM 调用，输入约 2–4k（需求 + 上一版计划），输出约 1–2k。
2 轮 ≈ +6–10k token；4 轮 ≈ +15–20k。
对比实测单次任务 300–500k token，**计划轮数开销 < 5%**，可接受。

## 10. M1 实现与冒烟结果（2026-10-23）

实现：`plugins/plan-rounds/`（`lib/index.js` 约 110 行、`bundle.patch.yml`、`README.md`）

- 命令 `/plan-rounds 0|2|4`：写入会话状态（command/run 事件，可回放、可续）
- 投影 `planRounds`：{ rounds }，客户端 useProjection('planRounds') 直接消费
- 系统提示段 `plan-rounds:contract`：按轮数注入「先写 PLAN-v1..vN（每轮严格评审上一轮）→ 冻结 ACCEPTANCE.md → 实现 → 逐条验收」

冒烟（单文件离线计算器，defaultRounds: 2，WB Proxy）：

```
PLAN-v1.md (55 行) → PLAN-v2.md (68 行，含 "Rejected as not acceptance-grade" 逐条否决)
→ ACCEPTANCE.md (65 行，37 条) → verify-calculator.mjs (503 行) → calculator.html
```

对照 batch31：软规则下 ACCEPTANCE.md 只有 1/12；改成「文件链 + 轮数契约」后单次即落地。

**踩坑记录**：profile patch 插入新插件必须用 `- insert: [...]` 包裹；平铺的 `- id: x / name: y` 会被静默忽略（无报错、插件不加载）。
