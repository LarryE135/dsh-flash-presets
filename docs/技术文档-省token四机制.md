# 省 Token 的四套机制（含上下文管理）· 详细说明

> 对象：dsh-flash-presets 的 lean-v3 预设（`presets/flash-lean-ptc-v3.patch.yml`）。
> 四个机制分别作用在**四个不同的时刻**，合起来才构成完整的上下文管理。
> 口径：DSH 0.2.1-rc.5；数字均可在仓库文件里逐行核对，行号已标出。

---

## 总览：四个机制各管一段

| # | 机制 | 作用时刻 | 实现位置 | 可逆 | 每次会话都省 |
|---|---|---|---|---|---|
| 1 | 轮次压缩 | 上下文**存量**过大时 | `compaction-basic`（L113-121） | 否（摘要不可还原） | 长会话才触发 |
| 2 | 工具输出裁剪 | 工具结果**进上下文**时 | `tool-result-pruner`（L124-129） | 否（中段丢弃） | 是，逐条生效 |
| 3 | 关插件 | **系统提示组装**时 | 6 条 `disabled: true`（L153-202） | 是（改回来即可） | 是，固定收益 |
| 4 | 行为纪律 | 模型**每一步决策**时 | persona 规则 6/7/8/9（L34-45） | 不适用 | 取决于模型配合 |

一句话概括四者的分工：**3 减固定开销，2 减单次输入，1 减历史存量，4 减未来发生量。**

## 机制 1 · 轮次压缩：把历史换成摘要

### 配置（`presets/flash-lean-ptc-v3.patch.yml` L113-121）

```yaml
- id: compaction-basic
  name: '@deepseek-ai/dsh-compaction-basic'
  config:
    thresholdRatio: 0.25      # 默认 0.8
    retainTokens: 20000       # 默认按比例，不写则按 retainRatio
    compactionRetries: 1
    auto: true
```

### 它到底怎么算

`dsh-compaction-basic` 的判定（源码 `lib/index.js` L132-134）：

```text
thresholdTokens = floor(min(contextWindow × thresholdRatio, pressureBudgetTokens))
retainTokens    = config.retainTokens ?? floor(messageBudgetTokens × retainRatio)
if (retainTokens >= thresholdTokens) throw 配置错误
```

- 到达阈值后，把**较早的轮次**交给模型摘要（`summarizationProvider` / `summarizationModel` 可指定），
  只保留最近 `retainTokens` 之内、按 token 估算的近期轮次。
- 所以它是**有损压缩**：被摘要的那段对话不再以原文存在。`compactionRetries: 1` 表示摘要失败重试一次，
  再失败就放弃本次压缩（不会卡死会话）。

### 为什么必须改这个数（关键算例）

该路由声明 1,000,000 上下文窗口：

| 阈值 | 触发点 | 实际效果 |
|---|---|---|
| 默认 0.8 | 约 **80 万 token** | 绝大多数会话根本到不了，压缩形同不存在 |
| v3 的 0.25 | 约 **25 万 token** | 长会话一定会触发，且保留 2 万近期轮次 |

预设注释里记了实测现象：**长会话里大量步数停在 300k 以上**——正是 0.8 永远够不着的那段区间。
这就是把 0.25 叫作「最大的一笔」的原因：不是压缩算法变强了，是**让压缩真的发生**。

### 代价与误伤

- 摘要本身要花一次模型调用（是有成本的，不是免费）。
- 被摘要掉的内容不可恢复：端口号、哈希、路径、判据数字，之后要重新取（再花一次工具调用）。
- 压缩时机对所有任务一视同仁，没有语义判断——它不知道你正处在「刚拿到关键参数，准备照着做」的节点。

## 机制 2 · 工具输出裁剪：只留头尾

### 配置（L124-129）

```yaml
- id: tool-result-pruner
  name: '@deepseek-ai/dsh-compaction-tool-result-pruner'
  config:
    thresholdChars: 8192      # 单条结果超过 8 KB 才裁
    headChars: 4096           # 保留前 4096 字符
    tailChars: 1024           # 保留后 1024 字符
```

### 机制

单条工具结果超过阈值时，中段被替换成固定标记（源码常量 `PRUNE_MARKER`）：

```text
[... tool result middle pruned ...]
```

最终长度约 `4096 + 标记 + 1024 ≈ 5.1 KB`。仓库的写法里有个硬约束（源码 L43-44）：
**`headChars + 标记长度 + tailChars` 必须 ≤ `thresholdChars`**，不满足直接抛错——所以这三个数不能随手乱配。

### 为什么这么裁（头 4096 / 尾 1024 的比例不是随便定的）

- 命令输出**头**通常是结构：表头、清单开头、文件列表前几十行。
- 命令输出**尾**通常是结论：报错堆栈的最后一行、测试汇总、退出状态。
- **中段**才是重复内容：同一批文件的后半、日志的连续行。

### 与机制 1 的区别（这是最容易混的一点）

|  | 裁剪（pruner） | 压缩（compaction） |
|---|---|---|
| 粒度 | 单条工具结果 | 整段对话轮次 |
| 时机 | 结果**进上下文时**，逐条 | 存量超阈值时，偶尔 |
| 方式 | 截断（留头尾） | 摘要（重写） |
| 可逆 | 否 | 否 |

### 误伤场景

`grep` 命中上千行、错误信息恰在中间、长 JSON 中间某个字段才是要找的——这三种情况下 8192/4096/1024 会把你要的那段切掉，
而且**不会提示**。对策是规则 6：先管道 `head -40` 或重定向到文件，用方法把范围缩小，别指望裁完之后翻。

## 机制 3 · 关插件：让工具 schema 根本不进系统提示

### v3 关掉的 6 个（L153-202）

| 插件 id | 它提供的工具/能力 | 关掉的代价 |
|---|---|---|
| `tool-subagent-codex` | `subagent_codex`（调 Codex） | 失去 Codex 子代理 |
| `tool-subagent-claude-code` | `subagent_claude_code`（调 Claude Code） | 失去 Claude Code 子代理 |
| `workflow-ptc` | 工作流引擎（PTC 版） | 失去 workflow 工具组 |
| `tool-workflow` | `tool_workflow*` 工作流工具 | 失去工作流编排 |
| `tool-ralph` | `ralph` 循环执行工具 | 失去批量循环执行 |
| `tool-plugin-manager` | 插件市场/管理工具 | 失去在会话里装卸插件的能力 |

### 为什么这是「零成本收益」

`disabled: true` 的插件**不加载**，因此它的工具定义（名字 + 描述 + JSON Schema）**不进入系统提示**。
每个工具定义通常几百到一千多 token，六个是一笔固定开销，**与任务难度无关**——短会话里它的相对占比尤其高。

与另外三个机制的区别：机制 1/2/4 都要「看情况」，机制 3 是**恒定折扣**，而且改回来只需删一行。

### 边界

它是能力和成本的交换，不是纯优化。如果你的任务真的需要工作流或 Codex 子代理，这个预设会直接不给你。
这也是为什么仓库保留 v1（更全）——v1 没关这些。

## 机制 4 · 行为纪律：控制「往上下文里写什么」

前三个机制管的是**已经产生的**内容；这一条管**还没产生的**。它是四者里唯一依赖模型配合的，也是长期收益最大的一条。

### 四条规则（原文在 L34-45）

**规则 6 · Output budget**
- 独立的调用合并进一次；长输出用管道或重定向（`| head -40`，或重定向到 `/tmp/out.log`）。
- 一句话：**永远不要打印你本可以 grep 的东西。**

**规则 7 · 程序化工具调用（PTC）**
- 3 个以上独立调用折成**一个** `run_code` 程序；只有一次调用时直接调。
- 关键在副作用：**中间结果留在程序里，只有你 print 出来的才进上下文**。这条对上下文的影响比前三条加起来都大。
- 配套：`tool-presentation` 设 `mode: ptc`（L194-197），工具面上只有 `run_code` 可直接调用。

**规则 8 · Context discipline（文中标注为 measured 最大杠杆）**
- 只读**新增**内容；派生数据用 grep/脚本从文件重建，而不是把同一份内容第二次读进上下文。
- 笔记保持短而事实化：`NOTES ≤ 60 行`。

**规则 9 · 增量写作**
- 文件只创建一次（骨架），后续用 `edit` 补；**不重复输出未改动的文件**。
- 两次 shell 补丁失败就换编辑器，别在同一个循环里烧上下文。

### 静态侧的两个配合项

| 项 | 配置 | 作用 |
|---|---|---|
| `agent-instructions` | `maxBytes: 65536`（L59-62） | AGENTS.md 最多读 64 KB，防止项目说明无限膨胀 |
| `persona.suffix` | 13 条规则全文约 1.2 KB | 这是**唯一必须每轮都付**的固定成本（换来行为约束） |

### 边界

这条全靠模型自控：规则可以写得很准，模型也可以不照做。它不会像机制 2 那样强制生效。
所以它省下来的量随模型而异，不能像前三条那样算出一个确定数字。

## 把四个机制串起来：一次会话里的上下文流水线

```text
静态侧    关插件（工具 schema 少 6 份） + AGENTS.md ≤ 64 KB + 13 条规则 ≈ 1.2 KB
   ↓
输入侧    工具调用 → 结果进上下文前先过 pruner（>8 KB 截成 头 4096 / 尾 1024）
   ↓   （规则 6/7 决定「调几次」：合并调用、重定向、只用 run_code 打印需要的部分）
存量侧    上下文变长 → 到 25% 窗口触发 compaction（早期轮次摘要化，保留 2 万近期 token）
   ↓
隔离侧    subagent / subagent_fork 自带独立上下文，主会话只收到它的结论（不继承中间过程）
```

四个机制不是并列的四个技巧，而是**同一条流水线上的四个闸门**：静态侧决定起点有多低，输入侧决定每步涨多少，
存量侧决定涨到哪开始回落，隔离侧决定要不要把活挪到另一个上下文里做。

## 四个机制的正面对比

| 维度 | 1 压缩 | 2 裁剪 | 3 关插件 | 4 纪律 |
|---|---|---|---|---|
| 生效时机 | 存量超阈值 | 每条结果进上下文 | 组装系统提示 | 每一步决策 |
| 是否强制 | 强制 | 强制 | 强制 | 靠模型自控 |
| 可逆 | 否 | 否 | 是 | 不适用 |
| 额外成本 | 一次摘要调用 | 无 | 无 | 无 |
| 误伤方式 | 早期细节丢 | 中段丢 | 能力缺失 | 模型不照做 |
| 我的实测 | 长会话必触发（预设注释记录 300k+ 现象） | 逐条生效，逻辑确定 | 固定少 6 份 schema | **未量化** |

诚实说明：**逐轮 token 数我没有精确统计**。上面能拿出的实测只有两类：
① 相同任务的工具调用数与耗时（另一组实验里 38 次 / 239 秒 对 68 次 / 438 秒）；
② 配置是否真的生效（`dsh --dump-config` 里能看到 `thresholdRatio: 0.25`、`retainTokens: 20000` 等取值）。
「省了多少 token」目前是**结构性推理**，不是测量结果——这句话在视频里建议保留，比含糊的百分比可信。

## 三个值得在视频里讲的判断

1. **压缩阈值是四个机制里唯一「改数字就见效」的一项**，其余三个都要靠结构（关插件、裁剪比例、规则）。
2. **裁剪和压缩都不可逆**，所以它们是「用信息换成本」，而不是免费的优化——讲清代价比讲收益更有说服力。
3. **规则 7（PTC）的省法和其他三条性质不同**：它让中间结果**根本不产生**，而不是产生后再删。
